# SwiftChart brand kit

Everything needed to brand SwiftChart: the guide below, the tokens, fonts, logos, app icons and reference components. The apps carry almost no styling yet; this is what to apply to each of them.

## In this folder

| Path | What it is |
| --- | --- |
| `README.md` | This file: the folder guide, then the brand guide. |
| `tokens.json` | Every token: colors for the light and dark themes, type families and styles, spacing, radius, shadows and sizes. Each token's `usage` note says where it goes and the contrast it reaches. The source of truth. |
| `tokens.css` | The same tokens as CSS custom properties, `@font-face` rules and one class per type style. Light by default, dark with `[data-theme="dark"]` or the system setting. Font URLs are relative to this file. |
| `fonts/`, `licenses/` | Sora, IBM Plex Sans and IBM Plex Mono (Latin, WOFF2) and their SIL Open Font Licenses; React's MIT license for the previews. |
| `assets/Logos/` | The lockup (color and reversed PNG) and the mark (SVG). Read its README before using them. |
| `assets/App-icons/` | App icons (SVG and 1024px PNG), the 180px Apple touch icon, the 32px favicon, the macOS-grid version, and `desktop/`: the five files the desktop app's `tauri.conf.json` lists, under the same names. |
| `assets/Originals/` | The logo artwork as it appears in the course deck, for reference only. |
| `components/` | Ten reference components. Each folder has a README (when and how to use it, its states and its markup), `preview.html` (open it in a browser; add `?theme=dark`) and `light.png` / `dark.png` renders. `bundle.css` holds their classes (prefix `sc-`), which the apps should reproduce in their own markup. `bundle.js` and `index.d.ts` are the React previews and their props; the apps don't use React. |
| `components/index.html` | All the previews on one page, with a light/dark switch. |
| `cover-light.png`, `cover-dark.png` | The kit's cover. |
| `CLAUDE-CODE-PROMPT.md` | The prompt for implementing the brand across the repo with Claude Code. |

## Using it in the code

- Load `tokens.css` (or generate the same custom properties from `tokens.json`) before any other stylesheet, and serve the fonts from the apps themselves: the on-site server and the desktop app must work with no internet.
- Build components from the token variables only, never raw hex values, so both themes come for free. `components/bundle.css` shows every state in that form.
- Follow the system's light or dark setting by default; `[data-theme]` on `<html>` overrides it.
- Where to apply it: the shared stylesheet both web apps load (`src/Ehr.Design/wwwroot/css/ehr.css`), the desktop app's (`src/Ehr.Desktop/frontend/app.css`), and the desktop icons (`src/Ehr.Desktop/src-tauri/icons/`, replaced by `assets/App-icons/desktop/`).

Components added to the shared stylesheet since the kit, in its style:

- `sc-btn--compact` as a link in a chart list's panel head ("Add allergy"), and the "Change" link on the right of an entry (`sc-list__actions`): entries are changed or given another status, never deleted, so no list has a delete action.
- `sc-chart`: the chart in three columns (`sc-chart__col`), each a stack of panels, so no panel leaves a hole beside a taller one: the standing facts (allergies, medications, diagnoses, vital signs, and the link to their history), then the notes and orders, then results, appointments, messages and the portal; recent visits across the foot. One column on a narrow screen. Each panel's first row is its head: the title on the left and its one action on the right ("Add allergy", "New order"), over a hairline, drawn from the title and the `p.sc-actions` after it; a sentence in the action's place (off-site) is the first line under the head.
- `sc-acting`: the band under the portal's app bar while someone is looking at a record shared with them ("Shared record. You're viewing …'s record, not your own."), with the button back to their own beside it, or under it on the portal's column, at `control-height` so the band stays a band. It is on every page, so nobody has to remember whose record they opened.
- `sc-thread` and `sc-message`: a conversation, oldest message first, each in its own bordered block with who and when above the text. The reader's own messages are set in from the left with an accent bar (`sc-message--mine`); every message also says who wrote it, so the bar is never the only sign. To a patient, staff are "Your care team" and they are "You".
- `sc-appbar__count`: a count beside an app bar link, as on "Inbox": mono, navy on mint, as a pill, shown only when it isn't zero, and read out as "Inbox, 2 to do".
- `sc-list__actions`: a record line's own actions, as plain links on the right of the line's text (`sc-list__main`), such as an active order's "Change" and "Discontinue…". Links, not buttons, because each opens a page; a destructive one ends in "…" and its page's button is the danger button, which names the action ("Discontinue order").
- `sc-dialog`: a native dialog opened modally, as the warning before a session ends (the plan's step 18): `surface-raised`, a `line` border, `radius-lg` and `shadow-dialog`, at most `width-form` wide, its title in `sc-dialog__title` and its buttons in `sc-dialog__actions`, the primary one first and focused. Its words say what will happen and when ("You'll be signed out soon", "… in 1:58 unless you stay signed in."), with a countdown that isn't read aloud every second; Escape is the safe choice. No motion.
- `sc-signed-out`: what takes a page's place when its session ends: the "Signed out." notice saying why, whether what was typed is kept, and "Sign in again", which opens the sign-in in a borderless frame below (`sc-signed-out__frame`). Nothing of the page that was there stays on screen.
- `sc-back`: the way back ("Back to patients"), as a small muted breadcrumb with a drawn chevron on the line above the page (`sc-pagehead`), the page's own actions on the right of that line as compact buttons. Underlined on hover and focus. Where a page has two ways back (a result opened from the inbox), both breadcrumbs sit together on the left, and a way on beside one ("Open the chart") has a list link's weight. In the portal it is at 16px and as tall as a portal control.
- `sc-sectionhead`: a section's heading with what belongs to it on its right, such as a day's heading on the schedule with "Previous day" and "Next day" as compact buttons.
- `sc-list__main`: wraps a record line's text, so the line is a row with its actions (`sc-list__actions`) on the right, on the first line's baseline; where several actions would squeeze the text below 16rem, they go under it.
- `sc-table__fit` and `sc-table__actions`: a table column only as wide as its values (a date, an MRN, a name), and the last column with a row's actions on the right, one line and one baseline, its links drawn like compact quiet buttons beside its buttons, and its quiet buttons with a button's edge (`line-strong`), so a button that acts at once is never taken for a link that opens a page. The column given neither takes the rest of the width.
- `sc-empty`: a list or table with nothing in it, as one quiet framed line on `surface-raised` ("Nothing needs your action."), so the empty space reads as meant; in the portal with a portal card's corners.
- Links in a table or a list of record lines are semibold and underlined only on hover and focus: their place makes them links. Links in running text keep the underline. Table rows tint `surface-subtle` under the pointer, and a keyboard shortcut on a control (`sc-kbd`) is a chip tinted from the control's own text, not a bordered box.
- A row's header in a table (`th scope="row"`, a result's name) is on its row's ground, not the header's, and takes the row's tints with it: `surface-subtle` under the pointer, `row-flagged` when the row is flagged. Only the columns' headers stay in view as the page scrolls.
- A plain link beside a form's buttons ("Cancel", in `sc-actions`) is a quiet control: semibold `accent-ink`, as tall as the buttons, underlined only on hover and focus; in the portal at the portal's size and height.
- `sc-btn--quiet sc-btn--danger`: a destructive action among quiet ones, the quiet button in the `danger` ink, such as a staff row's "Disable account". Where the action stands alone, its page's button is the bordered danger button.
- `sc-formcard`: a form, or one task's words and its form, in a card on `surface-raised` with a `line` border, on the page's left edge, its fields the card's width and a heading in it a panel's. In the clinic it is `width-form` wide with `radius-md` (`sc-formcard--wide`: `width-reading`, for a note's or a message's form); in the portal it is a portal card as wide as the column, its buttons at their own width and as wide as the card on a phone. A form never stands bare on the ground, and a form under what it adds to (a new staff account under the staff) is a card at its own width, not stretched to the table's.
- `sc-sheet`: a panel on a page opened from the chart, its title over a hairline as the chart's panels are (results to enter, vital signs to record, a note's addenda and visit summary); a form in it lays its fields side by side, as many as fit. `sc-split`: two columns that both earn their place, a form beside what it adds to (an addendum beside its note), one column under 64rem; `sc-split--even`, two equal columns, for panels two to a row (an appointment and what can be done with it) or a request beside its answer. `sc-formgrid`: a form of short fields, the item or name across the card and the details two to a row. `sc-notedoc`: a signed note as one document, each section's title on the left of its text between hairlines, the signer and the time first. `sc-editor`: the note editor, each section a row, its name and what to cover on the left and its box on the right, the buttons under the boxes.
- `sc-rows`: a list as rows on one card, as the portal's appointments, conversations, refill requests, forms, sharing and who viewed the record are: what a row is about on the left, semibold, its date or state on the right (`sc-rows__end`), a muted line under it (`sc-rows__meta`), and its buttons under its words. A row that opens something (`sc-rows__link`) is a target as big as the row and tints `surface-subtle` under the pointer. On a phone, one column, the right-hand part under the rest and a row's button as wide as the row.
- `sc-titlebar`: the page's title with its one action on the right, such as "New message" beside "Messages", under it where the line is too short. (A clinic page puts its actions on the line above its title, in `sc-pagehead`.)

# Brand guide

SwiftChart is an electronic health record for a small clinic: a clinician web app on the clinic's own server, a read-only copy of it off-site, a patient portal, a desktop app that keeps working offline, and dictation that proposes note fields for a clinician to review. This system is the brand for all of them. The apps carry almost no styling yet, so this is the guide to apply as each one is built out. Each surface below starts from the same mark, the same two colors and the same three typefaces, then tunes density and tone for who is using it.

The brand in one line: **calm, fast, exact**. A clinician is busy and a patient may be worried, so screens are quiet, text is plain, and nothing decorative competes with the record.

## The logo

The mark is two half-discs, offset: navy (`brand-navy`) on top with its flat edge down, mint (`brand-mint`) below with its flat edge up, separated by a thin gap. The wordmark "SwiftChart" sits to its right in a heavy geometric sans.

- **Lockup** (`assets/Logos/swiftchart-lockup.png`) on white, `surface-subtle` or any light ground. **Reversed lockup** (`swiftchart-lockup-reversed.png`: white wordmark and upper disc, mint lower disc) on `brand-navy` or `appbar`.
- **Mark alone** (`swiftchart-mark.svg`, `swiftchart-mark-reversed.svg`) where the name is already on screen or space is tight: favicons, the desktop title bar, loading states.
- **Round badge** (`assets/Originals/deck-badge-on-navy.png`): the mark above the wordmark in a white circle with a mint ring. For title slides, stickers and print only; the apps never use it.
- **App icon** (`assets/App-icons/`): the dark icon (navy square, reversed mark) is the default for the desktop app, the web apps' home-screen icon and the favicon. The light icon is for dark docks and dark slides only.
- **Clear space**: keep empty space around the lockup equal to the height of one half-disc on every side. **Minimum size**: the lockup at 96px wide; the mark at 16px tall.
- The wordmark is artwork. Use the lockup files; never retype "SwiftChart" in a font to stand in for it. In running text the name is plain text: "SwiftChart", one word, capital S and C.
- Don't recolor the mark beyond its two versions, swap the halves, close the gap, rotate it, outline it, add shadows or gradients, or put it on photos or busy backgrounds. The colored gradients in the course slide template belong to that template, not to SwiftChart: put the logo on a white or navy card, as slide 8 of the deck does.

## Voice and content

Write like a careful colleague: one short sentence that says what happened or what to do, a second only if the person needs it to act. Plain words; no "please", exclamation marks, emoji or chained clauses. Sentence case everywhere ("Sign note…", not "Sign Note"). Address the person as "you"; the system never says "I". Say who acts ("unless someone chooses to show them", not "until someone asks").

Rules:

- **A notice starts with its state, as its own short sentence** in `sc-notice__state`, ending in a full stop, then an ordinary sentence: "Saved. The patient can now see these results.", "Not saved. Fix the highlighted fields and try again." With nothing to add, the state alone: "Results acknowledged." Standing states too: "Read-only.", "Emergency access.". The word carries the meaning; the color only supports it.
- **Empty states are short and alike** ("No active medications.", "No results yet."), but a clinical difference stays: "No allergy information recorded" is not "No known allergies".
- **Status words are short and literal**: "Signed · read-only", "Awaiting review", "Left empty", "Mine (not saved)".
- **A notice that answers an action takes the focus** (`tabindex="-1"`, `data-focus-on-load`); a form that comes back with mistakes puts the cursor in the first field to fix instead.
- **Buttons are a verb and its object, the same words for one action everywhere:** "Sign note…" in the editor (a confirmation follows) and "Sign note" on it. "Cancel" only abandons a form; never "OK", "Submit" or "Yes". What does something is a button, what opens a view a link, and a page has at most one primary button. Back links say where: "Back to chart", "Back to home" (portal).
- **Don't narrate the system's bookkeeping** unless the person needs it to decide. It stays, once and plainly, for sensitive items, emergency access and what a patient is told about who can see their record.
- **A rule leads with the one thing that matters**, the rest in a short list or a "More about …" disclosure. A warning may be shortened but never lose what it warns of; the consent read aloud before listening, crisis-line text and clinical sources' words are never reworded.
- **Dictation proposes; the clinician decides.** Say "proposed" and "awaiting your review", never "diagnosed" or "filled in for you", and what was not carried over and why ("dictation never places orders or changes the allergy list"). A form opened from a proposal quotes the words as said.
- **Clinician screens can be terse**, with MRN and clinical abbreviations, but no internal words ("My patients", never "your panel") and no table name, column name or raw ID where a name exists, except on the administrator's pages.
- **The portal is for patients**: everyday words ("share your record", not "proxy"; "a standard file other clinics and health apps can read" before "FHIR"), labels spelled out, results explained plainly, no internal IDs or audit details: **Who viewed my record** says who looked, when and at which part.
- **One name per thing**, clinic and portal alike: "Messages"; "Refill request" (staff) and "Ask for a refill" (patients); "Visit summary"; "Enrollment code", "Setup link", "Invitation".
- **Dates** in clinician views and tables are `YYYY-MM-DD`, with 24-hour times, on the clinic's clock and labeled with its zone: `2026-11-15 14:05 CST`. The clinic has one configured time zone (`Ehr:Clinic:TimeZone`); the label is the zone's abbreviation for that moment (`CST`, `CDT`), or its offset (`UTC-6`) where no abbreviations are configured. A date with no time needs no label. A field that takes a time says which clock, without the abbreviation, since the time typed may fall on the other side of a clock change: "Taken (clinic time)". Label every time, in a table of times too: a screen reader lands on one cell at a time.
  - The desktop app shows its offline copy's times the same way, in the clinic's zone, not the laptop's.
  - **The audit log is the exception: it is in UTC, labeled "UTC".** It is the record of what happened when, read across sites and long after, and one clock with no daylight saving is the one that can't be misread.
  - The portal writes a result's date out for patients ("Nov 2, 2026") and shows its times on the clinic's clock, labeled with the zone, as clinician pages do: "09:30 CST".
  - Never show a time with no label, and never the reader's own device's zone.
- **Names** in clinician views are charted "Family, Given" ("Rivera, Ana"); the portal greets patients by given name.

## Color

Two brand colors, both from the logo: `brand-navy` (#0E1B2C) and `brand-mint` (#5FD4BA). Navy carries the brand; mint is a small accent that never carries text on a light ground (1.8:1 on white). Where mint has to read as text or a focus ring in the light theme, use `brand-teal` (#0B6E5C), the same hue darkened.

- Text is `ink` (body, headings) or `ink-muted` (metadata, hints) on `surface`, `surface-subtle` or `surface-raised`. Links and accent text are `accent-ink`.
- One primary action per view, filled with `primary` and labeled in `on-primary`. That is navy in light and mint in dark.
- `appbar` stays dark in both themes, so the reversed lockup always sits on it.
- Status: `danger` for errors, high-criticality allergies, the offline dot and emergency access; `warning` for read-only and pending states; `success` for saved, signed, synced and online; `info` for neutral system news. Each has a `-soft` background for notices and chips. `success` and `danger` are close in lightness, so a status is never shown by color alone: it always has a word, and on dots the word sits beside the dot.
- Transcript highlights: `highlight-unclear` marks passages the speech model was unsure of; `highlight-source` marks the words a proposed field came from. Audit rows that need review use `row-flagged`.
- Two themes, Light and Dark, with the same tokens. Follow the operating system's setting (`color-scheme: light dark`). The dark theme's ground is `brand-navy` itself, so the brand sets the mood even there.

## Typography

Three families, all open-source (SIL Open Font License) and served from the apps themselves, never from a font CDN: the on-site server and the desktop app must work with no internet. The files are in `fonts/` (Latin subsets, WOFF2). They load with `font-display: swap`, so text shows at once in the fallback font, and no page preloads them: the patient search page must fetch nothing ahead (a test that guards patient information holds it to that), so no page does. Sora and IBM Plex Sans are the course deck's own pairing.

- **Sora** (`--font-display`) for headings and display text only: `display`, `title-1`, `title-2`, `title-3`. Never for form labels, tables or body text.
- **IBM Plex Sans** (`--font-sans`) for everything people read and operate: `body`, `body-strong`, `body-sm`, `label`, `caption`; and `portal-body` (18px) as the portal's default body size.
- **IBM Plex Mono** (`--font-mono`) for things people compare or type character by character: `mono-id` (audit row IDs and other IDs compared character by character), `mono-shortcut` (keyboard shortcuts and quick-text triggers such as `.nad`) and `mono-code` (authenticator keys and recovery codes, letter-spaced). An authenticator key is shown in groups of four; a recovery code is shown exactly as it was issued, since that is what the person types back.
- **Dates, times, MRNs and readings** are IBM Plex Sans with tabular figures (`font-variant-numeric: tabular-nums`), so they line up from row to row without reading like a terminal, and never break mid-value.
- One `title-1` per page. Headings follow the page outline (h1 to h3) and are never chosen just for their size.

## Layout and spacing

Spacing comes from a 4px base (`space-1` to `space-16`). Clinician screens are dense: `space-2` to `space-4` inside panels, `control-height` (36px) controls, `body-sm` in tables. The portal breathes: `space-6` to `space-12`, `control-height-portal` (44px) controls, `portal-body` text and a single column at `width-reading`. Forms sit in one column in a card (`sc-formcard`) at `width-form` (in the portal, the column's width), and clinician pages max out at `width-content`. Every page stands on `surface-page` (the subtle grey in light, the navy in dark), and what is on it, panels, tables, toolbars of filters, sits on `surface-raised` with a `line` border, so each has an edge.

The patient is always visible. On every clinician screen about a patient, the patient banner sits directly under the app bar and stays put while the page scrolls.

## Shape, borders and depth

Corners are small and precise: `radius-sm` for controls and tags, `radius-md` for panels, notices and the banner, and `radius-lg` only for dialogs and portal cards. `radius-full` is only for status dots. Separate things with `line` hairlines and `surface-subtle` panels, not shadows. Shadows (`shadow-float`, `shadow-dialog`) only lift layers that float: menus, autocomplete lists and dialogs.

The mark's motif, two offset half-discs, is for brand moments only: sign-in, the portal welcome, empty states, the loading state and slides. Don't put it inside working screens.

## Iconography

SwiftChart has no icon set of its own yet, and the apps use none today. When icons arrive, use **Lucide** (ISC license): outline icons at 20px with a 1.75 stroke, colored `currentColor` so they take the text color. Ship the SVGs inside the apps; don't load them from a CDN. An icon always sits beside its word, except in a toolbar, where it has a tooltip and an accessible name. Status icons follow their status color, never the brand colors.

## Focus, motion and accessibility

- Every interactive element shows `focus` as a 2px solid outline, offset 2px, when focused from the keyboard. Never remove it.
- Clinician screens are keyboard-first (NFR-12): every common task can be done without a mouse, focus starts in the first field, and shortcuts the apps already have ("/" for patient search, Alt+Shift+D to dictate) appear on their controls in `mono-shortcut` and in `aria-keyshortcuts`.
- Motion is short and functional: 120ms to 200ms ease-out for opening menus, showing notices and updating rows. Nothing moves in the record itself. Respect `prefers-reduced-motion`.
- A value marked entered in error is struck through in the muted ink (`sc-struck`), with "entered in error" and the reason in words for a screen reader; it is shown only when asked for. A mark that a value is up or down from the one before (`sc-trendmark`) is a small triangle in the muted ink with the words beside it for a screen reader: never a color, since up is not good or bad by itself.
- A trend chart (`sc-trend`) is never the only way to read its numbers: a sentence under it says what it shows, and a table has every value. The line and points are `ink`, the reference range is a band of `success-soft`, and a value outside the range is a diamond filled with `warning`, so shape tells it apart as well as color. Charts are SVG drawn by the server, colored by the stylesheet's classes.
- Text meets WCAG 2 AA (4.5:1, or 3:1 at 24px and up) on its stated grounds in both themes. Controls, focus rings and status dots meet 3:1. Each color token's note gives its ratios.

## The surfaces

### Clinician web app (on-site)

The main product, for clinicians at the clinic. App bar: `appbar` with the reversed lockup on the left, then the work (Patients, with its "/" shortcut drawn as a keycap, Schedule, Inbox with its count, and Staff and Audit for an administrator); on the right, a step quieter, the staff member's own pages (Quick text, Passkeys), a hairline, the signed-in name and "Sign out". The current item gets a 3px `accent` underline; the one under the pointer a faint one. Under it, the patient banner on every patient page: name, MRN, date of birth and gender. Where the page reads the patient's allergies (the chart, the order form, the entry forms, the history of the chart's lists, the discontinued orders, the note, dictation, listening and review pages, and the expansion's pages for results, vital signs, messages, proxies, refill requests and appointments), the banner shows them too: high-criticality ones as a danger chip, "No known allergies", or "No allergy information recorded" in `ink-muted`. A patient page that doesn't read them has no allergy area, rather than a "none recorded" the page hasn't checked. The banner is on `surface-raised`, so it stands off the page's ground. Dense layout (`body-sm` tables, 36px controls) at `width-content`. One primary button per screen: "Sign note…" on the note editor, "Sign note" on its confirmation. A signed note shows a "Signed · read-only" tag beside its title.

### Off-site access (cloud copy)

The same app, served from the cloud copy when the clinic is unreachable. It looks the same, with three differences: the app bar shows an "Off-site" tag next to the lockup; the full-width warning notice sits under the app bar on every page ("Read-only. The clinic's server can't be reached, so nothing can be saved until it's back. …"); and each save action is taken off the page, with a sentence in its place that says what can't be done and why ("New orders need the clinic's server. Active orders remain readable."). Never leave a gap where an action was; say why it isn't there.

### Patient portal

For patients. Light app bar (`surface-raised`, `line` bottom border) with the full-color lockup, or the reversed lockup in dark. Its contents sit on the reading column: the lockup over the page's left edge and the account and "Sign out" at its right, with the links on a row of their own underneath; the links are `ink-muted`, the current one `ink` with the accent underline. Navigation: "My record", "Results", "Appointments", "Messages" and "Sharing". Larger and calmer: `portal-body` text, `display` for the welcome line, 44px controls, cards with `radius-lg` and `space-6` padding, and a single column at `width-reading`. The home says whose record it is as one line of facts, then a card each for results, appointments, messages and the rest of the record, each card's words on the left and its buttons in one column on the right (one column, the buttons full width, on a phone). Lists are rows on one card (`sc-rows`); results are such rows that open in place. Results lead with one plain-language sentence, with the clinical value and its reference range underneath. Registration, sign-in, "Forgot password" and "Send a new link" sit in one card (`sc-card`) at `width-form`, a little above the middle of the window, with the lockup at its top on the form's left edge and the form's button as wide as the card; the clinic's sign-in, code and account pages and the pages that stand on their own (an error, too many attempts) use the same card. On a phone the page is the card.

A question with set answers, such as each question of a pre-visit form, is a radio group (`sc-choice`): a fieldset whose legend is the question, each answer a full-width label with its radio button, `control-height-portal` (44px) tall, bordered in `line-strong`, its border `primary` and its ground `surface-subtle` once chosen. The arrow keys move between a question's answers, and the radio button shows the focus ring.

A form's answers, once sent, are a list of its own (`sc-answers`), in the portal and on the clinician's pages: each question in `ink-muted`, then the answer chosen beneath it in semibold, at every width and no wider than `width-reading`; a clinician's page follows a scored answer with its score in `ink-muted`. Not the two-column list of a record's facts, which suits short labels: a question is a sentence.

### Printed pages

Any page prints as its content (`@media print` in `ehr.css`): no app bar, no buttons, and nothing marked `sc-screen-only`, the class for what means nothing on paper, such as "use your browser's Print command" or a link that changes the view. The bands under the app bar print, without their buttons: a shared record's printout says whose record it is ("Shared record. You're viewing …'s record"), and an off-site one that the copy may be behind the clinic's server ("Read-only. …"). The ink is `brand-navy` on no ground in either theme: for print the stylesheet sets the color tokens again, to the brand's own colors, which no theme changes, or to nothing, so a page viewed dark still prints dark on white, and a status still reads by its word. Tables print whole, a row isn't split across two sheets, and a heading stays with what follows it. The portal's printable record (`/portal/record/print`, step 13b) is the page made for it. Paper never says that sensitive items were left out: "Sensitive items hidden" is on screen only; once they are shown, that notice and each "Sensitive" tag print.

### Desktop app (macOS and Windows)

Same tokens and components as the web app, inside a native window, and the same frame: the page's ground, with its parts on raised surfaces. The sign-in to sync, the lock and the "Deleted" screen are cards at the form's width on the page's ground, as the web's sign-in is, their one way in as wide as the card. ### Dictation

Before the controls, "Language of this dictation" (the expansion plan's step 17): a select in the `sc-field` style, English first, then "Spanish, experimental (proposals in English)", with a hint under it in `sc-field__hint`, shown and read with the select only while Spanish is chosen, opening with an "Experimental" tag in the warning tone (`sc-tag sc-tag--warning`) ("Experimental Speak Spanish. The transcript stays in Spanish, and the proposed note is in English for you to check. You don't need to say punctuation. Up to 2 minutes in Spanish."); it is disabled while a dictation is under way, never remembered, and a Spanish transcript is marked `lang="es"`. Controls: "Dictate" (Alt+Shift+D) as the primary button, then "Stop" and "Cancel", and after them, while recording, the time left of the dictation's limit (`sc-timeleft`: "1:52 left", the minutes and seconds in `mono-id`, "left" in `body-sm` `ink-muted`), counting down from 3 minutes, or 2 in Spanish. The status line under them is a live region in `body-sm` ("Recording. Speak your note, then select Stop."), with a `danger` dot while recording. The time left changes every second, so it is not a live region: the status line says a minute ahead that it stops then, as the Listen page says it of a visit ("Dictation stops in a minute, at its 2-minute limit.", 3-minute in English), and when 30 seconds and 10 seconds are left. At the limit a warning notice under the status line says so, naming it, and what happens next ("The dictation stopped at its 2-minute limit. What you recorded is kept and goes on to the review. Start another dictation for the rest once you've reviewed it."), and the status line says the limit once, with the transcript's finishing ("The dictation stopped at its 2-minute limit. Finishing the transcript and proposing the fields…"). The transcript is a bordered panel: final text in `ink`, words still being recognized in `ink-muted` italic, and unsure passages under `highlight-unclear`, explained once by a notice ("Highlighted passages may be wrong…"). Proposed fields (History, Assessment, Plan) sit one per row, each with its status as a tag ("Awaiting review" warning, "Left empty" and "Not dictated yet" neutral, "Proposing…" info) and any check under it in `warning` text. Selecting or focusing a field paints its source words with `highlight-source`. Orders and allergy changes heard in the dictation are listed under "Orders and allergy changes you dictated", never filled in; those dictation proposes (the plan's step 15) are marked "Proposed order" or "Proposed allergy to add". On the review they are listed apart, under "Proposed orders and allergies", in the same rows as the proposed fields (an `ol.sc-proposals`, without numbers): the kind, the state as a tag ("Awaiting review" warning, "Ordered" and "Allergy added" success, "Dismissed" neutral), the clinician's words under `highlight-source` in the sentence they said them in, any check in `warning` text, and the way into the order form or the allergy form beside **Dismiss proposal**.

A dictation in Spanish (the expansion plan's step 17) is reviewed in English screens like any other: its transcript is Spanish (marked `lang="es"`), and a notice that starts "Translated from Spanish." says the proposals are translations to check sentence by sentence. Each proposed field is a list of **translated sentences** (`sc-translation`): every English sentence in `ink`, and beside it, or under it where the column is narrow, "You said:" and the Spanish it was translated from in `ink-muted` `body-sm`, one pair per row with a `line` rule between. Over every pair, across both columns, "Translated from Spanish. Check it against the Spanish beside it." in `info` `body-sm`, whether or not the field carries a warning, so no sentence reads as checked for having none. Hovering or focusing a pair tints it with `highlight-source`, turns its Spanish and that line `ink`, and paints its Spanish words in the transcript. Its accept button says "Accept translated" and the field's name.

Listening to a visit (ambient listening, the expansion plan's step 16) is a page of its own, "Listen to the visit", and asks first: the statement to read aloud in an `info` notice, who will speak and who agreed as radio buttons, and the agreement as a checkbox, then "Start listening" as the one primary button. Nothing is recorded before it. While listening, a line under the heading carries the `danger` dot with "Recording the visit: 3:12 of 20:00." (an `sc-status` that isn't a live region, so the clock isn't announced every second) and the tab's title starts "● Recording:"; the status line above it, the live region, says each change and warning and keeps it until the next, a warning (nobody has spoken for 4 minutes; a minute left before the 20-minute limit) in `warning` text, semibold (`sc-status--warning`), as an error is in `danger` (`sc-status--error`), each said once; the buttons are "Pause listening" (then "Resume listening"), "Stop and draft the note" (primary) and "Stop and discard" (danger), with the sentence on someone else coming in beside them. No transcript is shown in the room. After Stop, "Who is speaking" lists each voice with its first words and a "Choose who it is" select, none chosen ("Me", "The patient", and beyond two voices "Someone else in the room", when three were to speak, and "I can't tell"), and "Draft the note" stays disabled until every voice has a role, with "Name every voice to draft the note." in `body-sm` `ink-muted` under it, tied to it (`aria-describedby`), until then. When the visit can't be fetched or drafted, the actions under the status line are what can still be done: "Try again" (primary), "Discard the recording" (danger), or once the voices are named, "Open the draft". In its review, the transcript is a paragraph a turn, each led by who said it in `ink-muted` semibold (`sc-transcript__speaker`): words, never colour alone; "Reject every proposal and delete the conversation" is a danger button that wraps its words on a phone (`sc-btn--wraps`) rather than running past the window's edge.

### Sensitive items

Some of a chart is more private than the rest: mental-health and substance-use diagnoses, some others by their code, and anything a clinician marks. These are never on screen by accident.

- **Left out, not blurred.** A page doesn't receive sensitive items until someone asks. In their place an info notice says how many are hidden and ends with a plain link to see them: "Sensitive items hidden. 2 diagnoses or medications are not shown. Show sensitive items".
- **Showing them is logged, and the page says so.** Once shown, the notice reads "Sensitive items shown. Your view is logged." with "Hide sensitive items". Never show them without that sentence. Summaries and addenda follow the same pattern ("Sensitive summaries hidden.").
- **Tagged where they appear.** Each sensitive entry carries a "Sensitive" tag in the warning tone (`sc-tag sc-tag--warning`), after its text and before its actions.
- **Never in the patient banner, a notification, an email or a page title.** The banner shows allergies only.
- **In a form,** "Sensitive" is a checkbox with a hint under it that says what marking does. Where the system marks an item by rule, the hint says so; the clinician can't clear it.
- **Offline,** the desktop app doesn't keep sensitive items. Where they would be, a muted line says how many aren't kept and where to see them.
- **For a patient's proxy,** sensitive items don't exist unless the patient has allowed them: no count and no notice.

### Emergency access

When a clinician opens a patient who isn't one of theirs, a page asks for the reason before the chart opens ("Reason", 10 to 500 characters; button "Open the chart"). While access lasts, the patient banner carries an "Emergency access" danger tag with the time it ends, and a danger notice under it says once, plainly, that the access and the reason are logged and reviewed.

### Admin

Admins see "Staff" and "Audit" in the navigation. On the staff page each row's actions are one line on the right: the link to the desktop sign-ins, "New setup link" as a compact button, and the authenticator reset and the account switch as quiet buttons with a button's edge, "Disable account" among them in the danger ink; the form that adds an account is a card at the form's width under the table. Audit tables are dense: tabular figures for times, `mono-id` for row IDs at the text's weight, `body-sm` for names and actions, sticky `surface-subtle` headers, and the filters above with a "Show" button. From a 1280 window the audit log's columns are set: the time and who first, each ID whole, wrapping where it must so it can be read and compared, and the reason and the fields changed (a muted caption-size line) taking the rest. Rows that need review (emergency access) are tinted `row-flagged` and carry a danger tag; the color is never the only signal. Once reviewed (the plan's step 18) a row loses the tint and carries a neutral "Reviewed" tag, with a danger "Not appropriate" beside it when the review found so, and every emergency access keeps its "Open the review" link. The review page is two columns: the access's facts as a record (`dl.record`) in a panel with its events under them as an audit table, the patient by ID, and the review beside them in a panel (under them on a narrow window); while the access lasts, a notice at the top says until when, and that it can be reviewed once it ends. Then it asks "Was it appropriate?" with two radio buttons and a note before "Mark reviewed".

### Email

Account emails (confirming an address, resetting a password) are single-column (`width-reading`) on white: the full-color lockup at 140px wide, a `title-2` heading, `portal-body` text and one navy button with white text. Every email has a plain-text version, and none ever contains clinical details: later message notices only point the patient to the portal.
