# UC 15 — Work through the inbox

SwiftChart EHR · the expansion plan's step 3 · Tahseen Arnan · a proposed use case, not in the course document

## Staff workflow

Every clinical page's app bar has an **Inbox** link, with the number of items that need your action when there are any. The inbox lists them oldest first: when each arrived, what kind it is, one line saying what needs doing, and the patient, linked to their chart. **Mark done** takes an item off the list. **Done** shows what you have finished, newest first.

Both clinicians and admins have an inbox. An admin's items show a patient by ID only, as the audit page does: admins have no access to patient data.

The inbox starts empty. Each kind of item arrives with the feature that creates it: messages from patients, results to acknowledge, refill requests, and emergency accesses for admins to review (`docs/expansion/PLAN.md`, steps 5, 7, 13d and 18). Since step 10b, an addendum someone else adds to a note a clinician signed arrives too ("Addendum to your note"), with a link to the note; the clinician marks it done here (`docs/UC14.md`, TC-UC14-13).

## Decisions

- **Data.** One table, `ehr.inbox_items`: the recipient, the kind, the patient when it is about one, the table and row it came from, a one-line summary, when it arrived and when it was done. Patient data, since an item names a patient: row-level security is enabled and forced, and the write-audit trigger records every change.
- **Whose.** An item is its recipient's alone. Row-level security lets a staff account read and mark only its own; another clinician, an admin who isn't the recipient, and the patient see nothing.
- **Marking done.** The one change an item takes. The app role may update one column, `done_at`; a trigger sets the time from the database's clock, refuses a second marking and any other change. Nothing reopens or deletes an item.
- **Creating items.** No runtime role can insert one yet. Each later step adds the narrowest way for its own kind, and the summary carries no health details beyond what the kind implies.
- **The count.** One index lookup for each full clinical page, made inside the page's transaction so the database knows who is asking (`InboxCountFilter`). Not made for page fragments, posts or the portal. It says nothing about any patient, so it isn't an audited read.
- **Reads.** The inbox page names patients, so each patient named is one recorded read, as in a list of patients. An admin's page names none and records none.
- **Keyboard.** The app bar link, each item's patient link and each "Mark done" button are ordinary links and buttons in reading order: Tab and Enter do everything.
- **Off-site.** The inbox is read from the cloud copy, and "Mark done" is forwarded to the clinic's server. While that can't be reached the buttons are off the page, with "Marking an item done needs the clinic's server. Your inbox remains readable."
- **Desktop.** The desktop app doesn't show the inbox: nothing creates items yet, and an offline inbox would need its own sync.

## Limits

- Two things create items: a patient's message (step 5, `docs/UC17.md`) and an order's results (step 7, `docs/UC1.md`). A message item is marked done here or by replying; a result item only by acknowledging the results on their page.
- An item goes to one person. Sharing an item among a team isn't built.
- The list shows the first 50 that need action.
