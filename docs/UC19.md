# UC 19 — Read a patient's record through the FHIR API

SwiftChart EHR · the expansion plan's step 11 (proposed FR-53) · Tahseen Arnan · a proposed use case, not in the course document

## What a clinician's client does

- **Sign in to the clinical app first.** The API uses the clinical app's own sign-in: a clinician's account, with the password and the authenticator code. Its cookie is what the API reads; nothing else is accepted (not a portal account's, not the desktop app's token).
- **Ask what is served:** `GET /fhir/metadata`, the capability statement.
- **Read a patient:** `GET /fhir/Patient/{id}`, or find them by MRN: `GET /fhir/Patient?identifier={MRN}`, or `identifier=http://swiftchart.example/fhir/sid/mrn|{MRN}`. A search by MRN finds a patient only when you may read their record.
- **Read their record:** search by the patient, `GET /fhir/{type}?patient={id}`, or read one entry, `GET /fhir/{type}/{id}`, for:
  - `AllergyIntolerance`;
  - `MedicationStatement` and `Condition`, which leave sensitive entries out unless `show-sensitive=true` is added;
  - `Observation`, results and vital signs, or one category with `category=laboratory` or `category=vital-signs`;
  - `Appointment`.
- **The answer** is FHIR R4 JSON (`application/fhir+json`). A search is a `searchset` Bundle with every entry's address, `total` (how many matched) and up to 600 entries, newest first by each type's own date (below); what the search has to say besides (sensitive entries left out, a list cut at 600) comes as an OperationOutcome entry. A refusal or a failure is an OperationOutcome too.

## Decisions

- **Who.** A clinician, for a patient on their panel, or under emergency access already started in the clinical app, for as long as it lasts: the chart's gate (`Patients/Chart.cshtml.cs`). The API offers no way to start emergency access. Anyone else is refused before anything is read: 401 when not signed in to the clinical app (a portal account or a desktop token included), 403 for an admin or for a patient off the clinician's panel (a search by MRN aside, below). A refusal is never a redirect to the sign-in page. The policy is the Clinician policy, on the whole `/fhir` group (`Program.cs`); row-level security is the second layer, as everywhere.
- **The gate comes first.** A search asks about the patient before reading anything. A read by ID first asks whose entry it is, and nothing else; a patient's ID is gated whether or not there is such a patient, as the chart is, so an unknown patient is 403. An entry the database doesn't give the reader is 404.
- **A search by MRN tells nobody who is a patient here.** It finds the patient only when the clinician may read their record. Any other MRN, a patient's off their panel or one that is nobody's, gets the same answer: 200 with an empty `searchset` Bundle, the same byte for byte but for its self link, which repeats what was asked. Neither reads anything about a patient, so neither is recorded. (A mistyped MRN of a patient on the panel answers the same way: found nothing.)
- **The order of a search.** Each type comes newest first by its own date: allergies by when they were recorded, medications by when they were started, diagnoses by onset, results and vital signs by when they were taken, and appointments by their start; entries with no date come last. A search cut at 600 keeps the first 600 in that order.
- **Every read is recorded as the page's is.** One request is one read of the patient (`read`), or, when `show-sensitive=true` asked for sensitive entries, one read of the patient's sensitive items (`read_sensitive`), the chart's event. The capability statement and a refusal record nothing. Off-site, the events go to the cloud app's audit queue and are written before any of the answer is sent; if they can't be, the answer is a 500 with nothing of the record.
- **Sensitive items.** Diagnoses and medications marked sensitive, by their code or by a clinician, are left out of searches, which say how many were left out, and a read by ID of one is not found, unless `show-sensitive=true` is given. Then they are included and carry `meta.security` with the confidentiality code `R` (restricted). The parameter is named so because, in FHIR, a parameter named `sensitive` would read as a filter (Tahseen's choice). Allergies, results, vital signs and appointments have no sensitive mark.
- **Left out always.** Medications and observations entered in error, a blood pressure reading in error included.
- **Codes.** As the record has them, with their standard systems: RxNorm and FDA UNII for allergies, RxNorm for medications, ICD-10-CM for diagnoses, LOINC for results and vital signs, and UCUM for a unit that is its code's UCUM unit (otherwise the unit as text). An entry with no code, such as "No known allergy", is sent as text. The MRN is sent with the clinic's system, `http://swiftchart.example/fhir/sid/mrn`, and the identifier type MR. A diagnosis is in the category `problem-list-item`. Nothing is translated into another code.
- **Vital signs** carry the `vital-signs` category and claim R4's vital-sign profiles: heart rate, body temperature, respiratory rate, body weight, body height and body mass index their own; oxygen saturation the base profile, since R4's `oxygensat` asks for LOINC 2708-6 and the record holds 59408-5 (by pulse oximetry).
- **A blood pressure is one Observation for each reading** (Tahseen's decision, built on step 9c): LOINC 85354-9, claiming R4's `bp` profile, with its systolic (8480-6) and diastolic (8462-4) as components, each with its value in mm[Hg] and its reference range. **Its id is the reading's ID**, which the database gives the two values entered together, not the ID of a row; a read by either value's own ID is not found, and neither value is ever an Observation of its own. The two are put together by that ID alone, never by their time. Its time is the reading's; `issued` is the later of the two values', when the reading was whole. A search counts a reading once.
- **Appointments** carry their status, start and end (in UTC), length, reason and cancellation reason, and the patient and the clinician as participants, by reference with their names (there is no Practitioner endpoint), each with the status `accepted`, which FHIR requires and the record doesn't hold (Tahseen's choice).
- **Times** are instants in UTC; dates are dates.
- **Strict.** A parameter the capability statement doesn't list for that request is refused with 400, at `/fhir/metadata` too, as is a parameter given twice or a value the API can't use, such as an MRN no MRN could be (longer than 20 characters, or with a control character in it: the patient search page's rule); `_format` is taken when it asks for JSON. A type the API doesn't serve, or an ID that is no entry, is 404.
- **JSON only.** A GET whose `Accept` header doesn't take `application/fhir+json` is refused with 406 before anything is read. As RFC 9110 has it, the most specific range that matches decides, by its q: `application/fhir+json` itself, then `application/*`, then `*/*`; so `application/fhir+xml` alone is 406, and so is `application/fhir+json;q=0, */*;q=0.1`. `application/json` is taken as asking for the API's JSON, as `_format=application/json` is, unless `application/fhir+json` is named. `_format`, when given, decides instead, as FHIR has it. A browser's usual `Accept` takes anything, so it gets JSON. A write is 405, with `Allow: GET`, whatever it accepts.
- **Read-only.** Any method but GET is 405 with `Allow: GET`. Off-site, the cloud app forwards every write to the clinic's server, as it does for the pages and the other APIs: so a write sent off-site is answered by the clinic's server's 405, or, while that server can't be reached, by the cloud app's plain-text "Not saved: the on-prem server can't be reached." (503), which isn't FHIR.
- **Never cached, never shared across sites.** Every answer has `Cache-Control: no-store`, and none carries a CORS header: a page on another site can't read it.
- **Off-site reads** come from the cloud copy, which may be a moment behind the clinic's server.
- **No new runtime package.** The app writes FHIR's JSON itself. The tests check it with the Firely .NET SDK (BSD-3-Clause), offline, against R4's own definitions.

| TC-UC19-02, alternative flow | Sensitive entries left out, then asked for and recorded; emergency access; entries in error left out, a blood pressure reading whole; a patient with only blood pressures; a search past 600 | `TC_UC19_02_AlternativeFlow.cs` |

| TC-UC19-05, NFR-01 and NFR-03 | The API's reads at 50,000 patients: p99 under 15 ms on-site, under 20 ms excluding the commit off-site | `TC_UC19_05_Nfr01_FhirReads.cs` |
| TC-UC19-06, NFR-06 | Anonymous, admin, portal, desktop-token and off-panel callers refused with no data; a search for an off-panel patient's MRN answered as for nobody's; never cached; no CORS headers | `TC_UC19_06_Nfr06_Security.cs` |

Also: `FhirCapabilityTests.cs` checks that everything the capability statement declares works and nothing else is served; `FhirReaderTests.cs`, the order each type comes in, and that a read by ID is one query with no count; `FhirObservationsTests.cs`, that a blood pressure missing a value is never sent; `UcumTests.cs`, that every unit in the reference data and the seed is UCUM; `AuthorizationTests.cs`, that the API answers an anonymous request with 401. `FhirConformance.cs` is the check every answer goes through: a strict parse, then Firely's validator over R4's definitions and the profiles a resource claims. It can't check LOINC, RxNorm, ICD-10-CM or UNII codes themselves, which aren't in R4's package.

## Limits

- No paging: a search returns its first 600 entries, newest first, and says how many matched.
- No other resource types (Encounter, Practitioner, notes), no `_include`, `_count`, `_sort` or other parameters, no history, no XML, no writes.
- Only the clinical app's sign-in: no OAuth or SMART on FHIR, so a client must hold a signed-in clinician's cookie.
- Off-site, a write is answered by the clinic's server, or by the cloud app's "Not saved" text when that server is out of reach, not by an OperationOutcome.
- Results and appointments have no sensitive mark, so none is held back.
- Thyrotropin results seeded before step 11 keep the unit "mIU/L", which isn't UCUM; the API sends that as text.
