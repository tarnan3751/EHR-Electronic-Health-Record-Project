## Implementation and development base

Branch `feature/uc13-ai-field-review` starts at main commit `86dc093`, with UC 9/10 (PR #31) and UC 14 (PR #39) already merged. This is a separate UC 13 change set. The former UC 7/8 combined PR #26 is not a dependency: UC 7 (#28) and UC 8 (#38, replacing #30) are already incorporated in main. There is no replacement draft table or second clinical editor.

From an assigned patient's chart, choose **Dictate note**, or choose **Dictate into this draft** in the existing note editor. The existing recording/transcription screen streams the transcript, then retrieves and stages the validated result on the primary. The saved review shows the original transcript beside Subjective, Objective, Assessment and Plan (a review saved before the expansion plan's step 14, beside its History, Assessment and Plan), preserving source highlights, unclear passages, warnings, empty-field reasons and instructions not carried into the note. Focus or hover a suggestion/source warning to highlight its original words. Keyboard users can focus the native Accept, Reject and Edit controls; the first pending Accept receives initial focus.

Each field requires an explicit **Accept**, **Edit → Approve edited field**, or **Reject**. The next pending field receives focus after a confirmed save. Progress and errors are announced, and errors receive focus. Accepted means the original server-held value; editing records the clinician's replacement; rejecting records no approved value. Decisions alone do not change clinical note text. **Add approved fields and continue to note** requires every proposal resolved, then atomically transfers approved values through `NoteContent` into UC 14. Rejected/empty fields stay available for manual completion. Existing text is preserved: an explicit append checkbox is required before adding approved values to nonempty fields. Stale versions require comparison/reloading, rather than silently replacing a newer draft.

Continue with UC 14's autosave, signature preview, confirmation and immutable signed chart record. A saved review can be reopened through its draft's **Resume AI field review** link; the same draft URL remains the chart entry. Completed evidence remains accessible through **Saved AI reviews** on the draft and signed note (subject to the same owner/panel restrictions). If no usable proposals exist, the transcript remains visible and **Continue to note** provides the manual path without unnecessary field decisions. An unfinished recording can be discarded; a staged review cannot be batch-discarded to bypass its decisions.

## Data flow and state

1. The browser sends a patient/draft/version and random review request ID to `POST /api/dictation/sessions/for-note`. It never supplies an authoritative sidecar session ID or AI result. Authorization, panel access, draft ownership and version are checked before requesting a sidecar session.
2. The server creates a session with the authenticated owner's existing sidecar header, then persists its patient/draft/owner binding. A retry reuses that request ID and returns its saved binding. A new note uses UC 14's `ClinicalNotes.CreateAsync`.
3. Recording, audio sequencing, transcript updates, stop and result polling retain the original UC 9/10 endpoints/contracts. Desktop offline dictation routes remain unchanged.
4. Stage accepts only the review ID/version. The server looks up its binding and refetches the result from the authenticated sidecar, sanitizes it through the existing typed contract, checks terminal state, limits and half-open UTF-16 source ranges, and stores trusted provenance/transcript/fields. Discarded model extras cannot enter storage as proposals.
5. In one primary transaction, `NoteReviews.StageAsync` stores review evidence and pending proposals, sets the source draft's gate, and advances its version. No proposed content is copied to the draft's sections or Body.
6. `DecideAsync` records a terminal per-field decision and advances the draft's version. An accepted value comes from its immutable original; only an edited value comes from clinician input. The gate stays closed until explicit completion. Exact decision-key retries return the saved result; a different terminal decision conflicts.
7. `CompleteAsync` locks and validates the current source, checks all recorded decisions, preserves/validates existing manual content, applies approved text, clears the gate and records the imported version/completion audit in one transaction. Completion retries do not append twice.
8. UC 14 queries authoritative proposal/review records before signing, and its database guard independently repeats the pending/consistency check under the source lock. An unfinished recording binding also blocks signing until staged or explicitly discarded, so omitting the handoff cannot bypass review. Client flags and direct signature requests cannot bypass it.

Batch states: `recording → pending → completed`, or `recording → cancelled`. A terminal result with zero proposals transitions directly from recording to completed. Proposal states: `pending → accepted | edited | rejected`; decisions are immutable. Manual edits after a completed import are allowed: its imported version must be no greater than the current draft version, and UC 14 still requires matching structured content and the exact saved signature version.

## Proposed orders and allergies (the expansion plan's step 15)

FR-14 as reworded: dictation never places, saves or signs an order or an allergy change, but it may propose one. Of the instructions the dictation service lists as not carried over, it proposes an instruction to place an order or to add an allergy only when every word of its sentence is accounted for: a closed lead-in, the verb in one of its plain forms, determiners, an item the reference data names, by its own name or a common name mapped to it there (an orderable for an order, an allergen for an allergy to add; the common names, such as "penicillin", "latex" and "CRP", are in `db/reference/dictation-names.toml`), the item's quantities and a closed set of trailers, and nothing else ("Go ahead and order a CBC today", "Refill his lisinopril for 90 days", "I'll add penicillin to his allergy list"). Any other word in its sentence holds it back ("if he gets worse", "as needed", "for his wife", ", she said", "to check for anemia", "Continue omeprazole and refill the omeprazole"), and so does anything the reference data doesn't name, so a new drug, a misheard name or a test the catalog calls by another name that no common name maps is never proposed, only listed. The sentences next to it are read for what may take it back, those after it past line breaks: a short sentence after it holds it back unless it is accounted for, as another instruction, a step of the plan said with its verb ("Recheck in one week."), a heading, lead-ins alone or thanks, so "Nah.", "Oops." or "Hang on." do; the next sentence holds it back with a negation, a word of error or a condition anywhere in it ("She is not willing to have blood drawn today."); and closed lists of cues read the rest: a retraction, doubt or refusal after it ("Skip that.", "She declined it."), someone else, a report or a list of what not to do before it ("Mom insists.", "Not to do today. She is frail."). A proposal can still be wrong, and is the clinician's to dismiss. It never proposes an allergy's removal, resolution or update. Everything it doesn't propose stays listed under **Not carried over**, as every instruction was before. Proposals are found by the service's rules (`validation.py`), not by the model; the prompt and the note schema are unchanged. A result with proposals and no fields (its sorting unavailable) is staged with them, and its review offers them like any other's: they come from the rules on the transcript, not from the model (D8 and D17; `DictationProposalTests.A_result_with_proposals_and_no_fields_is_staged_and_its_review_offers_them`).

- **Staging.** A result's proposals are staged with its review, each at its place in the stored result, only if each is one of its listed instructions, of the same kind, once, at most twenty, from a final transcript, with a proposal's warnings (`TrustedResult`); one that isn't refuses the whole result (502). A proposal row (`ehr.ai_chart_proposals`) holds no text: its words are the review's transcript. The database stages one only as the stored result holds it, before the note is signed (`db/policies/55-ai-review.sql`).
- **The review.** Under **Proposed orders and allergies**, each proposal shows its kind ("Order" or "Allergy to add"), its state ("Awaiting review", "Ordered", "Allergy added", "Dismissed"), the clinician's words marked in the sentence they said them in and the one before, while it waits any warning with the words it points at, once ordered or added the way to that order or allergy on the chart, and, while the clinic's server can be reached, **Open in the order form** or **Open in the allergy form**, and **Dismiss proposal**. Moving into a proposal's actions shows its words in the transcript too. Off-site with the clinic's server cut off, the actions are hidden: "Opening or dismissing a proposal needs the clinic's server. The review remains readable." Only the dictating clinician sees them, as the review itself.
- **Deciding.** A proposal is decided once: ordered by signing an order in the order form opened from it (`docs/UC1.md`), recorded by adding an allergy in the allergy form opened from it (`docs/UC4.md`), each form filling in nothing from the words and applying every one of its checks, or dismissed here, which writes nothing to the chart. After a decision the review comes back with the cursor on the next proposal waiting, or on the section's heading when none waits. Decided first in another tab, a form saves nothing, its order or allergy included.
- **Nothing waits on them.** Proposals hold up neither completing the review nor signing the note, and signing doesn't decide them: the note being written and the signed note (near its top) tell their author how many wait, with the way to the review, where they can still be decided.
- **Sign-in.** A form's `proposal` in its address doesn't survive a sign-in, which drops a link's query (step 13b): after one, the clinician is on an ordinary form with no proposal, and opens it again from the review, which the note being written and the signed note link to while any proposal waits (`DictationProposalTests.A_sign_in_drops_the_proposal_and_the_note_leads_back_to_its_review`).
- **Audit.** Reading proposals is recorded, with the part of the page (a note being written, or the signed note's); the forms opened from one record the proposal's and its review's reads besides their own. Each decision is in the write audit, and the order or allergy it names in the proposal's row.

## Database and security review

`ai_note_reviews` references ClinicalDraft, Patient and StaffUser. It stores the server-created session ID/limits, starting/imported versions, batch state, timestamps and sanitized JSONB evidence. The evidence includes transcript, original fields, sources, warnings, empty reasons, excluded instructions and model/prompt/schema/code provenance. Session IDs are unique, and draft/state is indexed. `ai_field_proposals` has a composite review/patient foreign key, unique review/field and unique nullable decision key, immutable original, approved value and server-derived reviewer/time. Both use optimistic state concurrency tokens and restrictive foreign keys.

`ClinicalDraft.Body` remains plain text, and no desktop DTO, conflict resolver or sync receipt contract changes. Staging/decisions increment its version without changing its content; if its structured version was current it advances alongside it. Completion writes the existing structured HAP/Body representation. Legacy plain-text drafts retain UC 14's conversion behavior. Signed-note storage and immutability are unchanged.

All PHI reads go through `PhiReader` and generate existing read events. Runtime `ehr_app` receives SELECT/INSERT/UPDATE on the new tables; `ehr_read` receives SELECT only; neither receives DELETE. RLS is enabled and forced. A review requires the authenticated clinician, their own draft, matching patient and active panel assignment; proposals inherit the parent restriction. Assigned colleagues, admins, patients, disabled accounts and anonymous/invalid contexts see no private evidence. The existing clinical-area/API policies and antiforgery checks also apply. No PHI is sent to browser localStorage/sessionStorage, htmx history, application logs or audit details.

Every review mutation locks the same draft row used by UC 14's signing trigger, so concurrent staging/decisions/completion/signing serialize. Database triggers reject binding/original/evidence changes, invalid terminal decisions, completion with unresolved/missing fields, stale imported versions and review mutations after signing. Database-generated reviewer/time cannot be spoofed. Standard write-audit triggers cover both tables. The signing guard checks the cached gate **and** unfinished dictation bindings, persisted pending proposals/reviews and completion metadata. A cleared boolean alone grants no eligibility. The unique final-note/draft constraint and all UC 14 guards remain.

**Required human review:** AGENTS.md requires another person's line-by-line review of `db/policies` changes. In this change, review the explicit grants, recursive parent/panel RLS scopes, ordinary write-audit triggers, expanded signature guard, and `55-ai-review.sql` lock/transition rules. New trigger functions run as the invoker under forced RLS, pin `search_path`, and revoke PUBLIC execution; none introduces SECURITY DEFINER access. Prompt, model schema, dictation validation pipeline and desktop conflict resolver are unchanged.

The API writes only on the primary; cloud requests use the existing authenticated forwarding path, and disconnected cloud mode returns 503. A failed or ambiguous response leaves displayed text intact and never claims successful review. Stable keys support retry after an acknowledgement loss. Review requests time out in the browser after 35 seconds. Unsaved edited fields and unfinished dictation trigger a leave-page warning. No API receives client-authoritative identities, timestamps, review flags or original AI values.

## Limitations and operational behavior

- Review requires a live primary. Desktop offline recording/draft sync is unchanged; this PR does not introduce offline proposal decisions or an AI review UI inside the desktop application.
- Temporary sidecar audio/results retain their existing lifetime. After successful staging, the sanitized transcript/provenance and proposals survive independently in PostgreSQL. An unfinished, unstaged session that expires must be discarded before redictating or continuing manually. A sidecar session created during a failed binding race is temporary and expires normally.
- Closing/refreshing a page can lose edits never confirmed by the server; leave-page warnings and explicit failure status reduce this risk. JavaScript provides audio, autosave, inline failure preservation and highlighting; persisted review decisions also support native forms. No PHI browser storage is added.
- Step 15's proposals open one order or one allergy each: anything else an instruction names is placed from the chart. A proposal waits until it is decided, however long; there is no inbox item for one.
- Decisions are terminal. Correct an approved value in the ordinary note editor after completing review; the original review evidence remains immutable. Existing content can be appended with explicit consent; automatic overwrite/reconciliation is deliberately not provided.
- No real speech/model/GPU quality claim is made by deterministic integration tests. Existing dictation eval/known limitations still apply. Source highlighting supports clinical review; it does not establish medical correctness.
- This feature targets `main`. Opening/merging a PR and deployment are separate steps; security SQL still needs the repository's independent human review.

- `ClinicalDraft 1 → 0..* AiNoteReview`; `AiNoteReview 1 → 0..3 AiFieldProposal`. Each review also references one Patient and its owning StaffUser; each decided proposal references one reviewing StaffUser. Keep ClinicalDraft's existing zero-or-one ClinicalNote relationship.

- `AiFieldProposal`: Id, ReviewId, PatientId, Field, OriginalValue, State, ApprovedValue, DecisionKey, ReviewerId, ReviewedAt.
- `NoteReviews`: `BeginAsync`, `StageAsync`, `DecideAsync`, `CompleteAsync`, `DiscardAsync`; depends on EhrDbContext, PhiReader, ClinicalNotes, UserContext, AuditRecorder and NoteWriteAuthority. `TrustedReviewResult` is constructed only from the server's sanitized sidecar result; `ReviewResult` returns status/errors/version/receipt.
- `PhiReader`: add `AiReviewAsync`, `AiReviewsAsync`, `AiProposalsAsync`, `LockDraftAsync`; the lock delegates to Data's ClinicalDraftLock.
- `NoteContent.ApplyTo` is shared by UC 14 manual save and UC 13 approved-content transfer. `ClinicalNotes.SigningProblemsAsync` adds authoritative eligibility checks to the existing static manual checks.
- `ReviewModel` inherits PatientNotePage and uses NoteReviews for mutations, PhiReader for evidence; DictateModel/EditModel link the continuous workflow. The partial DictationApi handles the trusted sidecar-to-domain boundary. Existing signing and signed-note classes remain.

Presentation explanation: “AI text stays in separate pending evidence until the clinician decides on every field. Accept uses the original, Edit preserves both versions, and Reject copies nothing. A version-checked transaction adds only approved values to our existing draft. Both the application and PostgreSQL query the saved decisions before signing, so hiding a button or posting a false flag cannot bypass review. The shared draft lock prevents concurrent signing from racing staged proposals.”
