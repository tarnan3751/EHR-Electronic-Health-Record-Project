# UC 20 — Receive results from a lab

SwiftChart EHR · the expansion plan's step 12 (proposed FR-54) · Tahseen Arnan · a proposed use case, not in the course document

A lab's system is an actor of its own: it receives the clinic's lab orders and sends back their results, with no person signed in. It reaches the on-prem app through a door of its own, `/api/lab` (`src/Ehr.Web/Api/Lab`), and the database checks it again (`db/policies/76-lab.sql`).

## What a lab does

- **Hold the key.** The lab's key goes in the `X-Lab-Key` header of every request. The on-prem app holds the same key as `Ehr:Lab:Key`, and the database holds its SHA-256, which the migration job stores from `EHR_LAB_KEY`. Without a key on the app, the door isn't there.
- **Ask for orders:** `GET /api/lab/orders?since={watermark}`. The answer is `{"watermark", "more", "orders"}`: the lab orders signed by transactions from `since` up to the watermark that are still waiting for results, and the watermark to ask from next time. Asking from `0`, or without `since`, gives every order still waiting, as after a restart. At most 100 signing transactions' orders come at once; `more` says to ask again straight away.
- **What each order holds:** `{"id", "signedAt", "tests", "conditions"}`, and each test `{"code", "unit", "low", "high", "decimals"}`. Only the tests still waiting for a result are listed: an order partly filed by hand gets the rest from the lab.
- **Send results:** `POST /api/lab/orders/{id}/results` with `{"collectedAt", "results": [{"code", "value", "unit"}]}`, one sample's results for one order, in the units the hand-over named. 204 when filed, and 204 again when the same results are sent again, which files nothing more.
- **When results are refused,** the answer is `{"error", "message"}`: a fixed word and a fixed sentence, never anything about a patient, and nothing is filed.

| Status | Word | Why |
|---|---|---|
| 400 | `malformed` | Not 1 to 50 results, a test twice, a value missing, negative, 100,000,000 or more, or with more than four decimals, a unit missing, a field the contract doesn't have; or a hand-over asked for with anything but `since` |
| 401 | `unauthorized` | No key, a wrong key, or someone's sign-in sent with it |
| 404 | `unknown-order` | No lab order has that ID (any other order is unknown here too) |
| 409 | `discontinued` | The order was discontinued, perhaps while the lab worked on it |
| 409 | `closed` | The order's results were acknowledged |
| 409 | `different-result` | A test already has a different result, a clinician's or the lab's: the one on file stands |
| 413 | `too-large` | A body over 16 KB |
| 415 | `unsupported` | A body that isn't JSON |
| 422 | `not-reported` | A test the order doesn't report |
| 422 | `wrong-unit` | A result in another unit than its test's |
| 422 | `in-the-future` | Collected more than five minutes ahead of the server's clock: send it again later |
| 429 | `too-many` | Over the door's limit for the minute |
| 503 | `not-ready` | The database holds another key than the app: the migration job must run with the app's key |

## Decisions

- **An actor without an account.** Nothing a lab does is a person's. The door refuses a request that carries anyone's sign-in, and the database refuses a call with anyone signed in. Its audit events have no actor and the source `lab`; the admin audit page shows them as "Lab".
- **The key, checked twice.** The app compares the header with its key in fixed time before reading anything. The database is given the key's SHA-256 and finds it among the hashes it holds (`ehr.lab_keys`, which no app role can read), the way invitation codes are found (step 6c). SQL as the app's role without the hash is handed nothing and files nothing.
- **Only what a lab needs.** An order's ID, to file against; when it was signed, by the server's clock, so a lab's clock can't move the times it works from; the waiting tests with their unit, the clinic's range and decimals, so a lab keeps no copy of the ranges; and the codes of the patient's current diagnoses, so values can fit the patient. Not the patient's sex or age: every lab test has one adult range here, so nothing would use them. Never their name, MRN, birth date or ID, the order's details, medications, allergies or signer.
- **Sensitive diagnoses are withheld.** The database's own rule for the hand-over can't read a sensitive diagnosis at all, so none ever reaches a lab.
- **Every hand-over is recorded.** The database records a `sent_to_lab` event for each order it hands over, in the statement that reads it, with the order as its row and the patient: an order handed over again (a restart, a second lab) is recorded again. Each is a disclosure of that order's waiting tests and the patient's diagnoses.
- **Filed like a clinician's results.** The lab's results go through the database rule a clinician's filing does (`ehr.file_result`): the clinic's name, unit and range, final and released at once, the order resulted, and the clinician who signed it told in the inbox. The write audit records each write the filing makes as the lab's.
- **All or none, and once.** One order's lock is taken first, so two posts for one order, or a post and an acknowledgment or a discontinuation, go one at a time. A post the same as what is on file is answered as the first was; a post with a different value for a filed test is refused whole, the rest of it too.
- **By transaction, never by time.** The watermark is a transaction ID from the change log, as the desktop app's sync uses: an order signed in a transaction that commits late still lands in a later window. Lab orders signed before step 12 are not in the change log, and are resulted by hand.
- **Never cached, never through the internet.** Every answer is `no-store`. The cloud app has no lab endpoints: a GET there finds nothing and is held to sign-in (401, as any address with nothing there is), and a POST is forwarded to the on-prem app without `X-Lab-Key`, and refused (or "Not saved" while the clinic's server is out of reach). An on-prem app with no `Ehr:Lab:Key` has no door either, and answers the same way.
- **A flood is bounded.** The whole door takes `RateLimits:LabRequestsPerMinute` requests a minute (120 by default), together, whoever sends them, before the key is checked. A hand-over gives at most 100 orders, one audit event each, so the most the door can add to the audit log is 100 × 120 = 12,000 `sent_to_lab` events a minute, and only with the key: a lab asking from 0 again and again is held to that.

## Limits

- One lab, one key. A second lab would need a key of its own and a way to tell their orders apart.
- No corrections: a result once filed can't be changed by the lab, as by a clinician.
- When the clinician who signed an order can't be told (their account is disabled) and nobody has the patient on their panel, a result reaches no inbox; it is filed all the same (step 7's rule).
- Lab orders signed before step 12 are not handed over.
- Not HL7 v2 or FHIR: a contract of this project's own.
