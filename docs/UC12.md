# UC 12 — Open a chart through emergency access

SwiftChart EHR · Luke Garcia · CS 3354 Software Engineering, Fall 2026

## Clinician workflow

Search for the patient and open their chart. A patient on the clinician's panel opens straight away. For anyone else, the chart sends the clinician to **Break the glass** (`/patients/{id}/reason`), which shows nothing about the patient and asks why the chart is needed, in 10 to 500 characters. **Break the glass** records the reason and opens the chart with a notice that the access is recorded for review and when it ends. For four hours the chart, its notes and its note pages open to that clinician without asking again; after that the reason is asked for again. Admins see each use on **Audit** (`/admin/audit`), marked **Review** until an administrator reviews it, then **Reviewed** (the expansion plan's step 18, `docs/UC24.md`), and **Emergency access only** lists just those; each read there also says which part of the record it was for (its **Part**, step 13c2: the chart, a note's page and so on), and **Part of the record** lists one part's reads. The patient, and anyone they share sensitive items with, can see in the portal's **Who viewed my record** that the clinician used emergency access and when, but never the reason typed; the reason page says the patient can see the access (the expansion plan's step 13c, `docs/UC6.md`).

## Decisions

- **Who.** Clinicians only: the Patients folder of the Clinical area has the Clinician policy, so an admin is sent to `/denied` and someone signed out to `/sign-in`, whatever address they type.
- **Gate.** In the app, not the database (`Ehr.Domain/Patients/BreakGlass.cs`). Row-level security lets every clinician read every patient, as the team decided; the reason and the audit log are the control. The chart, the note pages and the reason page all check the panel first, then a grant that hasn't ended.
- **Reason.** Trimmed as it is bound (`Reason.cshtml.cs`), then checked: required, at least 10 characters, at most 500, each with its own message. `BreakGlass.GrantAsync` checks the same lengths again, so no other caller can record a grant without a reason.
- **Recorded twice, in one transaction.** A `break_glass` audit event with the reason, and a row in `ehr.break_glass_accesses` that lets the clinician back in for four hours, which the database puts in every administrator's inbox to review (step 18). The table's write-audit trigger records the row as well. Every chart view is a `read` event through the PHI reader, and a change from the chart, such as **Add to my patients**, is the trigger's `insert`.
- **Off-site.** The cloud app forwards the reason to the on-prem app, which saves it, over HTTPS only: the cloud app refuses an `Ehr:OnPrem:Url` that isn't `https://` (`Forwarding/OnPremApp.cs`). The chart's reads are served from the replica and reach the on-prem log with source `cloud`. With the clinic's server unreachable, nothing can be recorded, so emergency access isn't offered and the page says why; a reason typed just as the link drops is shown again on the "Not saved" page to copy.
- **Not cached.** The chart sends `Cache-Control: no-store`, as the note pages do, so it isn't kept on a shared computer's disk and Back after signing out doesn't show it.

## Limits

- Each emergency access is reviewed by an administrator other than its clinician once it has ended, through the inbox (the expansion plan's step 18, `docs/UC24.md`): until then the **Review** tag stays on it.
- The reason is stored as plain text in `ehr.break_glass_accesses` and `ehr.audit_events`; it is encrypted at rest only by the disk (TC-UC12-05).
- The four hours run from the grant. There is no way to end a grant early, and a new reason given while one is active adds a second grant.

## Sensitive items in the audit log (the expansion plan's step 2b, by Tahseen Arnan)

Admins have no access to patient data; the values a write changed, in an event's details, were the one place they saw any. For a sensitive item (a diagnosis or medication marked sensitive, `docs/UC4.md`) they no longer do.

- **What the page shows.** A write to a sensitive item is listed like any other, with when, who, what and which row, a "Sensitive" tag, and "A sensitive item changed. Its values aren't shown here." The copies the lists' history keeps are listed too, without values.
- **What the database does.** The write-audit trigger marks the event (`audit_events.sensitive`), and, when an item becomes sensitive, marks that item's earlier events. The runtime roles can't read `audit_events.details`. The page gets values from `ehr.shown_audit_details`, which answers only an admin and never for a marked event. The full record stays in the table, for a restore or a legal request handled outside the app.
- **Nothing unmarks an event,** and an event takes no other change, from anyone: a trigger refuses it.

Test case TC-UC12-07 (`tests/Ehr.Web.Tests/TestCases/UC12/TC_UC12_07_SensitiveValuesHidden.cs`) checks the page; `tests/Ehr.Security.Tests/SensitiveAuditSecurityTests.cs` checks the database.

## The audit log without clinical text (the expansion plan's step 18a, by Tahseen Arnan)

Tahseen's rule: "The admin audit view shows who did what to which record, but no clinical text for any patient data, sensitive or not." Since this step the audit page shows no value of patient data at all, sensitive or not.

- **What the page shows.** A change to patient data is listed with when, who, the action, the table and row, and "Fields changed:" with the names of the fields it changed: for an update those whose value changed, for an insert those it gave a value, for a delete those that held one. Never a value, and never a key inside a JSON column. A sensitive item's change still says only that a sensitive item changed (above), and the lists' history copies, patients' messages and refill requests still show nothing.
- **What counts as patient data.** An event that names a patient, or a table the write-audit trigger is on: the tables decided PHI in `ExpectedProtection` (`tests/Ehr.Security.Tests/ProtectionTests.cs`), which a test holds equal to the tables with the trigger. An event about no patient, such as a desktop sign-in, keeps its details.
- **Two names are left out.** An order's `safety_warnings` and `safety_override_reason` are set only when the patient has an allergy or a medication that weighs against what was ordered, so even their names would say something about the patient. The page never lists them.
- **The emergency-access reason** is still shown on the `break_glass` event, and on the review page (UC 24): it is the clinician's statement, written for the review (Tahseen, on step 18).
- **What the database does.** `ehr.shown_audit_details` gives an administrator the field names, worked out from what the write-audit trigger stored, so events written before this step are shown the same way. The values stay whole in `audit_events.details`, which no runtime role can read: nothing about what is stored changed.
- **The same off-site,** where the page is read from the cloud's copy.

Test case TC-UC12-09 (`tests/Ehr.Web.Tests/TestCases/UC12/TC_UC12_09_NoClinicalText.cs`) checks the page; `tests/Ehr.Security.Tests/SensitiveAuditSecurityTests.cs` checks the database.
