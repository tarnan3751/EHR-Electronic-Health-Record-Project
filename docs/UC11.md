# UC 11 — Sign in with multi-factor authentication

SwiftChart EHR · Luke Garcia · CS 3354 Software Engineering, Fall 2026

This file records what the expansion plan (`docs/expansion/PLAN.md`) has changed in this use case. The use case itself, and its first six test cases (`tests/Ehr.Web.Tests/TestCases/UC11`), are Luke's.

## A link opens its page alone after sign-in (the plan's step 13b)

Someone who follows a link while signed out is sent to sign in and then on to the page the link named. Before step 13b they arrived at the link's whole address, so whoever wrote the link chose what the page did on arrival: `?sensitive=true` on a chart showed the patient's sensitive items, recorded as the clinician's own view, and a link to the portal's record file downloaded it.

- **The rule.** After a staff sign-in the app goes to the page the link named with its query removed (`Links.LocalPage` in `src/Ehr.Web/Accounts/Links.cs`). It applies at every point the staff sign-in follows a return address: after the authenticator or recovery code (`Code.cshtml.cs`), on **Continue** after a first enrolment (`Enroll.cshtml.cs`), and when someone already signed in opens the sign-in page (`SignIn.cshtml.cs`). The password step only passes the address along. The portal's sign-in follows the same rule and keeps nothing.
- **What is kept.** A patient search's own criteria, `name`, `birthdate` and `mrn` (`SearchQuery.Parameters`), so a clinician whose session ended on a search comes back to it. Everything else is dropped, `sensitive` and page handlers included. On any page but the search those three only fill the "Back to search" link.
- **Still a local address.** The address is checked as a local one first, as before; anything else goes to the home page.
- **What this leaves open.** A link can still have a clinician run a patient search on arrival: up to 50 patients are listed by name, MRN and date of birth, and each is recorded as that clinician's read. Nothing is shown that the clinician couldn't search for, but the reads are ones they didn't choose, and the portal's "Who viewed my record" (step 13c) shows them to those patients. It waits for a decision: filling the form in without running the search would close it, and changes what `LoggingTests` expects.
- **Both sign-ins on one host.** A browser that holds a portal session and signs in to the staff app through a link to the portal's record file lands on the portal's download page, not on the file.

Human review: the three redirects above and `Links.cs` decide where an authenticated session lands, so they are listed with the authorization changes in the phase 4 pull request draft.

## Test case added by the plan

- **TC-UC11-07** (`TC_UC11_07_LinkOpensPageAfterSignIn.cs`): the cross-area link gives a page and records no download; a chart link with `?sensitive=true` through the code page, already signed in, and through a first enrolment each land on the chart without sensitive items and record no `read_sensitive`; a link with search criteria plus `sensitive` and a handler keeps only the criteria.
