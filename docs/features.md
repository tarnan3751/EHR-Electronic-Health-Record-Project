# What's built

## Working today

- AI field review (UC 13): dictate from a patient chart or draft, compare source-highlighted suggestions, explicitly accept/edit/reject every field, and add only approved text to the existing clinical draft. Decisions and provenance persist under forced RLS and auditing; authoritative app/database checks block signing pending reviews. See [UC 13 implementation and assignment guide](UC13.md).
- Clinical notes (UC 14): clinicians create and autosave Subjective, Objective, Assessment and Plan from a patient chart (notes and drafts written before the plan's step 14 keep their History, Assessment and Plan), reopen private drafts, and explicitly confirm a signed note whose text never changes (only its sensitivity can, with a reason: the plan's step 10b). Signing validates the saved version and server-held pending AI review, requires the primary, and records the signer, time and audit history. The editor preserves displayed work on failed requests. It extends the offline draft-sync model without changing its plain-text Body contract; see [UC 14 implementation and review guide](UC14.md).
- Orders (UC 1): from a patient's chart, a clinician with the patient on their panel signs a lab, imaging, medication or referral order, picked from a small synthetic catalog. The chart lists active orders. The database sets the signer and the time, records the write, and refuses a second active order for the same item without a reason. A signed order is never edited: a clinician discontinues it with a reason, or changes it, which signs a new order and discontinues the old one as replaced, and the chart keeps the discontinued orders with who, when and why. See `docs/UC1.md`.

- The desktop app (Tauri) shows the quick text list, and works offline. Phrases are kept in an encrypted local database (SQLCipher) whose key is made on first launch and kept in the macOS Keychain or Windows Credential Manager. Adds and edits are saved there first, in an outbox; a background sync, every 10 seconds and straight after a change, sends them and brings back what changed, from the on-prem app when it can be reached and through the cloud app otherwise. A change the server refuses comes back with both versions and **Keep mine** and **Keep theirs**, as on the page. Syncing needs a clinician signed in, with email, password and the code from their authenticator app; the session is kept in the Keychain or Credential Manager beside the database key, every sync request carries it, the server refuses it 12 hours after that sign-in, as it ends a web sign-in (see [UC 8](UC8.md)), and when the server ends it the app asks to sign in again. Signing out keeps the local copy. When an administrator revokes a clinician's desktop sign-ins, the app on each of their computers deletes everything it keeps there, its key included, the next time it reaches a server (the remote wipe, see [UC 7](UC7.md)). It updates itself from the same servers, asking first and never over the lock or a recording, and installs only a newer release signed with the key built into it; a server can refuse to sync with a build older than a minimum it names. The list can be read offline and signed out; changes need someone signed in. While someone is signed in, the window locks after 15 idle minutes, warned 2 minutes before, at the sign-in's 12-hour end, and at every launch, never over a recording; it covers the window without clearing anything, sync carries on, and it opens with the password, checked by the server or, with none, against a slow hash in the local database (see [UC 7](UC7.md)). The window shows whether it's online and how many changes are waiting. Every network call is made in Rust, not in the web view. Verified on Linux against the local server stack, including offline changes, conflicts and the off-site path; sign-in so far only against a stand-in server in its tests. CI builds it on macOS and Windows; it hasn't been run on a Windows PC yet.
- The web app (ASP.NET Core Razor Pages with htmx) serves the quick text page at `/quick-texts`: a shared list of phrases, each with a shortcut such as `.nad`. On-site, phrases can be added and edited; a save that started from an older version is refused and shows both versions, with **Keep mine** and **Keep theirs**. Off-site, the cloud app shows the list from the replica and forwards saves to the on-prem app; right after a save, that person's pages come from on-prem until the replica has the change. If the on-prem server can't be reached, or can't save because its database is down, off-site pages still load, every page says the system is read-only, a save says it wasn't saved, and signing out still works (see [UC 2](UC2.md)). Tests run the page against a real PostgreSQL 18.
- Sign-in and authorization. Staff and patients have separate accounts, cookies and sign-in pages (`Areas/Clinical/Pages/Account`, `Areas/Portal/Pages/Account`). Every staff sign-in takes a password and a code from an authenticator app, wherever it comes from; a new account enrolls its app at its first sign-in, and sees recovery codes once. Where the clinic has passkeys (`Ehr:Passkeys`), a staff member may add them at **Passkeys**, with a current code, and use one in place of the code after the password, on either staff site, the device verifying them each time; the authenticator app stays required, and patients and the desktop app have no passkeys (the plan's step 19, `StaffPasskeys`, `docs/UC11.md`). The on-prem app creates the first admin from `Ehr:Bootstrap` settings when there are no staff accounts; admins create the rest at **Staff**, each with a one-time setup link, and look after them there: a new setup link for a forgotten password, an authenticator reset for a lost phone or device, which removes the account's passkeys too, disabling an account, which locks it out and ends its sessions until it is enabled again, and revoking a clinician's desktop sign-ins, after which each of their computers deletes what the desktop app keeps there the next time it reaches a server (the plan's step 20, `docs/UC11.md`). Policies attach to whole areas (`Program.cs`): any staff account for the clinic's root (which sends a clinician to their patients and an admin to the staff page), clinicians for patients, admins for staff, patient accounts for the portal, clinicians for dictation (`/api/dictation`, with the staff cookie and the page's form token in a header, where a refusal is a 401 or 403 rather than a redirect, and an account disabled or locked out, or whose password changed, is refused on its next call), clinicians for the read-only FHIR API (`/fhir`, with the staff cookie, refused with a 401 or 403 rather than a redirect; see [FHIR API](apis.md#fhir-api)), and nothing anonymous but the sign-in pages, static files, and the desktop app's sign-in and updates. On the portal's own address (`Ehr:Links:PortalBaseUrl`, when it isn't the clinical app's), `/` redirects to `/portal` before any sign-in. Staff who sign in there land on the patient sign-in page, since their sign-in goes on to `/`: they use the clinic's address. Either sign-in, at its last step or when already signed in, goes on to the page it was sent from without that page's query, but for a patient search's criteria through the staff sign-in, so a link can't ask through it for a download or sensitive items (step 13b's review). The desktop app signs in at `/api/desktop/sign-in` with the same two factors and gets a session token, which every sync request carries; the token is a clinician's, works for 12 hours after that sign-in, and ends sooner at sign-out, when the password changes, or when an administrator revokes it, when the refusal says so (`Ehr-Sign-In: revoked`) and the app deletes what it keeps (`ehr.desktop_sessions`); its session's 30 days are how long the app may open its offline copy without a sign-in, after which the app locks it until a sign-in with both factors, deleting nothing. A web sign-in, staff or portal, on either site, ends 15 minutes after the last request made with it and 12 hours after it began, however active (the plan's step 18, `SessionTimes`): the cookie is renewed whenever a minute has passed, a page's question of how long is left (`/session`, `/portal/session`, with the `Ehr-Session-Check` header) never renews it, and a dictation or a visit isn't started when the 12-hour end would cut it off. Every signed-in page warns 2 minutes before the end, in a dialog whose "Stay signed in" keeps the session without reloading the page; a recording counts as activity and is never warned over; and at the end the page is taken off the screen, what was typed on it kept in the tab's memory for the same account to sign in again to (`session.js`, `docs/UC11.md`). No page served to someone signed in is cached (`no-store`, `NoStoreFilter`), so Back after the end shows nothing. The signed-in account reaches the database as `app.user_id`, where row-level security is the second layer.
- The first PHI table, patients, with row-level security enabled and forced, a write-audit trigger, and the PHI reader in `Ehr.Domain` that every read goes through and that records each one (`db/policies`, `Phi/PhiReader.cs`). A clinician's home is their panel: the patients they have added to it from the chart (`ehr.patient_assignments`, PHI like the patients themselves). A search by name, date of birth and MRN, combined, covers the whole clinic: it marks the patients on the clinician's panel as theirs and the rest as restricted, since opening one of those asks for a reason, says what to correct when criteria can't be searched (such as a date that doesn't exist), and the chart links back to the same results. Results also come as the clinician types, up to 20 at a time, since each patient listed is a recorded read; Enter lists up to 50, and asks for more letters or a date of birth when more match. The name field has the focus on arrival, `/` reaches the search from any clinical page, and the arrow keys move through the results. When the database fails, the search says it couldn't be completed and the chart that it couldn't be loaded, rather than showing a blank page; a chart that doesn't exist says so too. The chart shows demographics, the allergies, medications and diagnoses the patient has now, and their five latest visits with the latest one's blood pressure and heart rate, each section saying when nothing is recorded (and "No known allergies" apart from no allergy information); these live in their own PHI tables, shaped on FHIR like patients (allergies, medications and diagnoses can be edited, as below; a visit is created by checking a patient in for an appointment), and opening the chart is one recorded read of the patient. From the chart a clinician puts the patient on the panel or takes them off, and issues a portal enrollment code. Opening the chart of a patient who is not on the clinician's panel first asks for a reason (emergency, or break-glass, access): the reason is recorded as a `break_glass` audit event for admins to review, and the chart stays open to that clinician for four hours (`ehr.break_glass_accesses`). The database still lets every clinician read every patient, as the team decided; the reason and its review are the control. A patient registers at `/portal/register` with that code, confirms their email (a link that expired can be sent again at `/portal/resend`, an address that already has an account gets the same page as any other while its owner is told by email, and a new code replaces a registration that was never confirmed, such as one with a mistyped address), signs in, and sees their own record and nobody else's, and their test results at `/portal/results`: released results only, newest first, each with its normal range and what it means in plain language (`ehr.observations`, `Results/ResultExplanation.cs`; see `docs/UC6.md`); a forgotten password is reset through a one-time link sent to their address (`/portal/forgot`). The portal takes the patient from the session, never from a request. Off-site, pages that read PHI come from the cloud app's replica like any other page. The replica takes no writes, so the cloud app records those reads, and the sign-outs it handles itself, in its own audit queue, a file on its disk that is flushed before the page is sent, and ships them to the on-prem app every couple of seconds with a key both apps share (`src/Ehr.Web/CloudAudit`, `Api/Audit`), where they arrive with source `cloud`. So charts and the portal stay readable off-site while the on-prem server is down, and nothing read there goes unrecorded. Every view and change of patient information, and every sign-in, is in `ehr.audit_events`, which nothing at runtime can change (the database itself marks an event as about a sensitive item, and nothing else). Admins review it at **Audit** (`/admin/audit`): the newest events first, narrowed by action, staff account, patient ID and dates, with emergency access flagged. A patient sees who viewed their own record in the portal (step 13c, below), through one function that answers only for the record the session is looking at. Admins have no access to patient data, so a patient appears there by ID, and a change to patient data by the names of the fields it changed, never a value (the plan's step 18a, `docs/UC12.md`); the values the trigger records stay in the log.
- The sync API for the desktop app, at `/api/sync/quick-texts` on both servers (`src/Ehr.Web/Api/Sync`), for a desktop session token; the cloud app checks the token against its replica. A pull returns the phrases changed since a transaction-ID watermark, fed by a change log that a database trigger writes; a push applies batches of changes, each with an idempotency key, and returns applied, duplicate, conflict (with the saved phrase) or invalid for each.
- The local server stack runs the whole server architecture in Docker Compose: the PostgreSQL 18 primary, its streaming replica, Barman backups with point-in-time restore, which a drill rehearses on every push (`infra/compose/restore-drill.cs`), a simulated WAN, and an optional monitoring profile that emails the administrators when a site, the link to the clinic, replication, backups or a disk fails (Prometheus and Alertmanager; "Monitoring" in [infra/compose/README.md](../infra/compose/README.md#monitoring)). Every connection in it is TLS, verified against the setup's certificate authority, apart from the `ai` profile's calls to the models inside the on-prem server; the keys that protect cookies and form tokens are encrypted at rest with the sites' certificate; "Encryption" in [infra/compose/README.md](../infra/compose/README.md#encryption) says what the host's disk has to provide for the rest. Verified on Linux, and on an Apple Silicon Mac for replication, isolation, backups and restore; Windows is not yet verified.
- The database foundation: the app's roles (`ehr_owner` for migrations, `ehr_app` and `ehr_read` for the apps), the first table (`quick_texts`), and a migration job that brings the primary up to date every time the server stack starts. Security tests check the roles against a real PostgreSQL 18. See [Database changes](development.md#database-changes).
- CI (GitHub Actions) checks every push and pull request. `main` only accepts reviewed pull requests that pass it, and each commit on `main` publishes the web image. See [Continuous integration](development.md#continuous-integration).
- The dictation models download with one script, `src/Ehr.Dictation/setup_models.py`, which checks every file against the hash Hugging Face publishes: K2 Horizon 7B for note structuring and MedASR for speech to text, and, only when asked, Whisper large-v3-turbo for dictation in Spanish. See [Dictation models](dictation.md#dictation-models).
- Dictation, server side: MedASR transcribes as the clinician speaks, marking passages too quiet, too noisy or too uncertain to trust; K2 Horizon sorts the finished transcript into Subjective, Objective, Assessment and Plan (the plan's step 14); and every proposed value is checked against the transcript before anyone can see it, so one that isn't grounded in it, or that orders something or changes the allergy list, is never shown. What passes is pending until a clinician approves it, and nothing is stored. The on-prem app has a dictation API for clinicians; off-site, the cloud app forwards it. A test set of synthetic dictations measures it all, and CI checks the committed results against the prompt and checks in each commit. Measured on an Apple Silicon Mac; the accepted baseline is recorded on the server machine. See [Dictation](dictation.md).
- Dependency manifests and toolchain versions are in place. The dictation sidecar's and the eval's Python packages are locked, each in its `uv.lock`; `setup_models.py` lists its own version ranges.

- Editable allergies, medications and diagnoses, with standard codes. From the chart, a clinician with the patient on their panel adds and changes entries, picking each from ICD-10-CM, RxNorm or FDA UNII codes as they type; nothing is deleted, an entry gets another status, and a page lists the history of every change. Mental-health, substance-use and some other diagnoses are sensitive by their code, and a clinician can mark any diagnosis or medication sensitive: sensitive items are left out of the chart until asked for, and asking is recorded. An admin's audit page shows that a sensitive item changed and who changed it, never its values. The allergy list says whether nothing is recorded, there are no known allergies, or what the allergies are. The codes are the full ICD-10-CM and RxNorm lists, loaded from pinned source files by a script, never at runtime, beside LOINC lab orders and results, FDA drug classes and DDInter's interactions, which later steps use. See `docs/UC4.md` and `docs/expansion/reference-data.md`.

- A staff inbox (`/inbox`): what needs each clinician's or admin's action, with a count in the app bar, each item linking to its patient, and "Mark done". It starts empty; later features put their items in it. See `docs/UC15.md`.
- Emergency-access review (the plan's step 18, UC 24): each emergency access goes to every administrator's inbox but its clinician's; once it has ended, one of them opens it, sees who used it, the patient by ID, when, the reason given and what was done under it from the audit log, never a value from the record, and marks it reviewed as appropriate or not, with a note, once. That closes every administrator's item, and the audit page tags each access waiting or reviewed and can list the ones found not appropriate. See `docs/UC24.md`.

- Appointments (FR-17): clinicians book an appointment from a patient's chart, with any clinician, and reschedule it, cancel it with a reason, check the patient in (which starts their visit) or mark a no-show; `/schedule` shows any clinician's day; the database refuses a double booking. Patients see their upcoming and earlier appointments in the portal. There is no self-scheduling. See `docs/UC16.md`.

- Secure messages (FR-18): a patient writes to their care team from the portal, the message arrives in the inbox of each clinician who has them on their panel, and any of them replies from the conversation; clinicians can also start one from the chart. Every opening of a conversation is audited, the email about a reply says only that there is one, and the audit page never shows a message's text. See `docs/UC17.md` and `docs/UC6.md`.

- Proxy access (FR-19): a patient gives a family member or carer access to their record in the portal, or the clinic records it, with a scope and always an end date. The proxy signs in with their own account, which someone who isn't a patient creates from the emailed invitation, and chooses whose record to view; the database checks on every query that the access is theirs and in force, holds back sensitive items and messages unless the access includes them, and records everything under the proxy's account and the patient. See `docs/UC18.md` and `docs/UC6.md`.

- Results (the plan's step 7): a clinician files a lab order's results against it, the order becomes resulted, values outside their reference range are flagged and listed first, the clinician who signed the order finds them in their inbox, they or a colleague on the patient's care team acknowledges them, and the patient sees them in the portal. See `docs/UC1.md`.

- Ordering safety checks (the plan's step 8): a medication order is checked against the patient's coded allergies and drug classes, and against what they take for known interactions from DDInter, the ONC high-priority list and FDA labels. Serious warnings need a recorded reason to override. Decision support for this demonstration system, not a complete clinical reference. See `docs/UC1.md` and `docs/expansion/reference-data.md`.
- Vital signs and trends (the plan's step 9): blood pressure, heart rate, temperature, respiratory rate, oxygen saturation, weight and height are recorded as coded observations, with the body mass index worked out by the database; the chart lists the newest value of each, its vital signs page has the flowsheet, and vital signs and lab values have trend charts drawn by the server as SVG, with the reference range and a table of the numbers, for clinicians and in the portal (`docs/UC4.md`, `docs/UC6.md`).
- Addenda to signed notes (the plan's step 10): a signed note's text stays locked, and a clinician with the patient on their panel signs addenda that are shown after it with author and time. A note can be signed as sensitive and an addendum marked sensitive; both follow the rules for sensitive items. The desktop app's offline chart shows signed notes and their addenda, except sensitive ones (`docs/UC14.md`).
- Vital-sign corrections and ranges by age (the plan's step 9b): a wrong reading is marked entered in error with a reason, kept in the record and left out of every view unless asked for, and the correct value is a new reading; heart rate, respiratory rate and blood pressure are flagged against the range for the patient's age (`docs/UC4.md`, `docs/expansion/reference-data.md`).
- Vital-sign readings (the plan's step 9c): a sign has one standing value for a patient at a moment, whatever the visit, and a moment's visit is decided from the time it was taken, for all its values at once (a check-in ties the sets taken up to fifteen minutes before it to its visit, after Tahseen's answers); a blood pressure is one reading of a systolic and a diastolic, which the database keeps whole and marks entered in error whole, and which every page shows as one value, "126/80" (`docs/UC4.md`).
- Children's vital-sign ranges (the plan's step 9d): a child's heart and respiratory rates are flagged against Fleming et al.'s centiles for their age group, and a child's blood pressure against the AAP's screening table for their year of age and sex, as "needs follow-up", never High; readings already recorded were ranged again (`docs/UC4.md`, `docs/expansion/reference-data.md`).
- Note follow-ups (the plan's step 10b): an addendum written by someone other than the note's signer is labeled and reaches the signer's inbox; a signed note or addendum can be marked sensitive after signing, with a reason, and only the person who marked it or the note's signer can unmark it (`docs/UC14.md`). Marking a note marks its addenda as inherited from it, and unmarking the note clears only those marks (step 10e).
- Off-site audit cost (the plan's step 10c): off-site, a request's audit events are written to the cloud app's queue together, with one flush to disk, before any of the page is sent; a page whose events can't be written is not sent (`docs/UC2.md`).
- A read-only FHIR R4 API (the plan's step 11): a clinician's client reads a patient on their panel, their allergies, medications, diagnoses, results, vital signs (a blood pressure as one reading) and appointments, coded as the record is, with the clinical app's sign-in; each read is recorded as a page's is, and sensitive items are left out unless asked for. See [FHIR API](apis.md#fhir-api) and `docs/UC19.md`.
- Results from a lab (the plan's step 12): a lab's system, with a key of its own, is handed the lab orders waiting for results, with only what it needs, and files their results through the same database rule as a clinician's filing; each order handed over and each result filed is audited as the lab's. The simulated lab (`src/Ehr.Lab.Simulator`) plays one, in the local stack too, with results that fit each patient's diagnoses. See [Simulated lab](apis.md#simulated-lab) and `docs/UC20.md`.
- Visit summaries (the plan's step 13a): from a signed note, a clinician with the patient on their panel writes and releases a summary for the patient in three plain-language parts, refused while it has an internal code, an identifier, the patient's record number or a whole section of the note in it; the patient, and whoever they share their record with, reads it in the portal under the rules for sensitive items, and the patient is emailed that there is something new, with no health details. A released summary is never edited: a wrong one is withdrawn with a reason and leaves a dated placeholder in the portal. The notes themselves never reach the portal. See `docs/UC14.md` and `docs/UC6.md`.
- Download my record (the plan's step 13b): from the portal's home, the patient, or a proxy as their access allows, downloads their record as one FHIR R4 file (allergies, medications, diagnoses, released results, vital signs and appointments, from the FHIR API's own mapping, with ids made for the file) or opens it as a page laid out to print, with the visit summaries. Sensitive items only when asked for; never notes, entries in error or unreleased results; each download recorded apart from a view. Pages print without the app bar or buttons, keeping the bands that say whose record it is and that it is read-only. See `docs/UC6.md`.
- Who viewed my record (the plan's step 13c): the portal lists the views of the record in the audit log over the last 12 months, newest first, 50 a page: a staff member by name and role, "You", someone the record is shared with by the address the patient gave access to, or the lab's hand-over of a lab order, with which part, as each read records it (step 13c2: the chart, the lists, results, a visit note, the portal's own pages and so on; "Record" for most views recorded before that step), and a view through emergency access marked, never its reason. A proxy sees staff members' views, the lab's and their own: with sensitive items, every staff member's, as the patient does; without them, only those of staff who had the patient on their panel at the time, so never emergency access, and no views of sensitive items or of notes, and a part that could hint at something kept from them reads "Record". The database answers it, for the session's own record only (`db/policies/42-record-views.sql`). See `docs/UC6.md`.
- Refill requests (the plan's step 13d): from the portal's home, the patient, or a proxy whose access includes messages, asks the care team to renew an active medication coded as a product the clinic orders, with a short note, one open request a medication; each clinician with the patient on their panel finds it in their inbox, and one of them approves it by signing an order for the same medication product on the order form, with every check of an order, or declines it with a message the patient reads in the portal. The patient sees each request waiting, approved with what was ordered, or declined, and is emailed that there is something new, naming nothing. Sensitive medications follow the rules for sensitive items. See `docs/UC21.md` and `docs/UC6.md`.
- Pre-visit forms (the plan's step 13e): a clinician with the patient on their panel asks for the PHQ-9 or the GAD-7, worded as their authors publish them, before a booked appointment; the patient, or a proxy allowed sensitive items, fills it in in the portal from 7 days before the appointment until it ends; the database scores it, and the clinician sees each visit's score, severity band and need for follow-up, and a trend. Every form is a sensitive item. The forms say they aren't watched as they arrive and where to get help now; a PHQ-9 answer about self-harm also reaches the care team's inboxes. Nobody is emailed. See `docs/UC22.md`.
- SOAP notes and visit-type templates (the plan's step 14): a note is written in Subjective, Objective, Assessment and Plan, each required to sign, and the editor says what each holds; a clinician picks a visit type (follow-up, new patient, acute, well-child or telephone, kept as reference data) to see what to cover in each section, which is never put into the note; and asks for the latest day's vital signs (none entered in error, a blood pressure as one reading, each with its time) as text, which goes into Objective only when they add it. Nothing written before was moved: a note signed then keeps its History, Assessment and Plan, shown as signed, and a draft written then opens in the editor with its History in Subjective, to sort, and changes only when its author saves it. Dictation sorts into the same four sections; a review of a dictation sorted before them that is still waiting shows its History, which goes into Subjective once approved. See `docs/UC14.md`.
- Orders and allergies a dictation proposes (the plan's step 15, FR-14 as reworded): dictation never places, saves or signs an order or an allergy change, but the review of a dictation lists each plain instruction to place an order or to add an allergy as a proposal, in the clinician's words, labelled as heard and marked in the sentence they said them in, with what was heard after it (the next sentence whole, and those after up to another instruction, so a retraction the rules don't read is in view beside its button), to open in the order form or the allergy form, which fill in nothing from it and sign or save through every check they have, or to dismiss; each is decided once, and none holds up the review or signing (`docs/UC13.md`, `docs/UC1.md`, `docs/UC4.md`). The dictation service proposes them by its own rules, never the model's, and only an instruction in a closed sentence: every word of its sentence is accounted for: a closed lead-in, the verb in one of its plain forms, determiners, an item the reference data names, by its own name or a common name mapped to it there (an orderable for an order, an allergen for an allergy to add), the item's quantities and a closed set of trailers, and nothing else. Any other word, or anything the reference data doesn't name, holds it back (still listed), as does an unclear passage; a short sentence after it, read past line breaks and heading lines, must be accounted for too (a step of the plan, a heading with what follows it, or thanks), a negation, a word of error or a condition in any sentence within reach holds it back, and the sentences around it are otherwise read for closed lists of cues; a proposal can still be wrong, and is the clinician's to dismiss; the eval measures them, against what the rules allow and against every order or allergy to add a clinician would expect proposed (`docs/UC10.md`).
- Listening to a visit (the plan's step 16, UC 23), shipped switched off (`Ehr:Ambient:Enabled`, on in the local stack; the drafts are thin, field F1 0.3155 on the eval's synthetic visits, and the checks find an order or a question only in the forms they read, so that the last run offered none is true of its drafts, not a promise; switching it on is the clinic owner's decision, see `docs/UC23.md`): at the clinic only, a clinician confirms that everyone who will speak agreed aloud, which is recorded in the audit log before the microphone is opened; the page shows that it is recording the whole time, pauses when asked or when out of sight, stops at 20 minutes or after 5 minutes of quiet, and keeps nothing when discarded. After Stop, the clinician says who each voice is, with none chosen for them, and the note is drafted into the same review as a dictation, with the transcript a turn at a time and who said each passage; Subjective comes only from the patient's words, and says so. The conversation's transcript is kept apart and only while the review is open, never in the audit log, and the on-site app deletes it 7 days after it was written if nobody has finished the review (`Ehr:Ambient:KeepTranscriptDays` may only shorten that, to a day at the least; set it alike on both apps, whose reviews say it), after which its proposals can be rejected or edited into other words, but not accepted or edited back to the words offered. A conversation proposes no order or allergy. See `docs/UC23.md`. The dictation service tells the voices apart with a speaker-embedding model, transcribes the visit a turn at a time, and drafts the note a part at a time with a prompt of its own, under the speaker rules (see [Dictation](dictation.md#how-it-works)); the eval's twelve synthetic visits measure it (`eval/README.md`, Visits).
- Dictation in Spanish, experimental (the plan's step 17, proposed FR-61): the Dictate page asks the language of each dictation, English first and never remembered, and labels Spanish experimental. A dictation in Spanish is transcribed by Whisper large-v3-turbo, finished passages only, up to 2 minutes, with a passage not heard as Spanish marked and left out of what is sorted; K2 Horizon proposes the four fields in English, each sentence with the Spanish passages it was translated from; and the dictation service checks every sentence against that Spanish before anyone sees it, class by class and in order, refusing what it can't compare: its numbers with their units and what each measures, how long, how often, dates, drugs, what is done with each drug and habit and when, sides, routes, dose forms, severity, abbreviations, what can be ordered, opposites, a few findings never to be added, negation, certainty, history and relatives. It doesn't check the meaning of other words: the review shows each sentence beside its Spanish for the clinician to compare. Nothing beyond the note is proposed from Spanish: the instructions its detectors find, in Spanish or in English, and the Spanish of any sentence whose English is one, are cut from the note and listed for the clinician to place. Whisper is optional, and a server without it refuses Spanish; the desktop app's offline recordings stay English. A dictation made with English chosen fewer than two thirds of whose words are English (Spanish dictated with English chosen) offers nothing: its transcript stays as plain text, with words pointing at the Spanish choice. The Spanish eval's results are committed (`eval/results/latest-es.json`, beside the English text run's, `eval/results/latest-en-text.json`, the Spanish texts' cap), and the eval gate fails when a value from Spanish is shown changed from what was said without a warning the owner hasn't accepted, an instruction is carried into a field, or any of the review's wrong translations that reverse the meaning passes the Spanish checks without the owner's acceptance. On 2026-11-25 he accepted, as known limits in his name, what run B and the review show (17 values counted as changed, 8 of them Whisper's hearing; 41 wrong translations that pass; English content F1 0.4069 and 61 of 140 fields discarded on the recordings, against lines of 0.5 and a third), with the gate capped at those counts and a Spanish baseline at run B's numbers (`docs/UC9.md` and `docs/UC10.md` give the numbers as they are).
